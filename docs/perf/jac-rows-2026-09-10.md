# `jac_rows` / `q_rows` — which residual rows are ever WRITTEN

Closes item 4 of `remaining-2026-09-10.md`, and with it the half of item 7 (the
stamp) that was blocked on it. VerA now emits the predicate; the engine consumes
it to delete whole residual rows at comptime.

Commits: ARPice branch `jac-rows` (the commit carrying this file), VerA
`jac-rows-vera` a5da976.

## The predicate

Two new optional device declarations, one `u64` each:

```zig
pub const jac_rows: u64 = 0x00000000000000fd;  // mos1: `eval` writes 7 of 8 rows
pub const q_rows:   u64 = 0x000000000000003a;  // mos1: `q` writes 4 of 8 rows
```

**Bit `ru` is set when the emitted half contains any `res[ru] = ...` at all.**
Not "the row can be nonzero", not "the row has a live partial" — *the generator
emitted an assignment to it*. A clear bit therefore means the row is literally
`S.con(0.0)` on every path, at every bias, for every parameter set, and the host
may delete the entire row: the residual add, the charge-plane add, the `q_tape`
slot and the Jacobian columns.

Omitted above 64 unknowns, exactly like `jac_pattern`. Absent means all-ones,
which is the dense behaviour every host had before — hand-written devices
(`tests/testdev.zig`) and runtime `.so` devices from an older generator keep
working untouched, and no `abi_version` bump is needed because the slot tape's
layout does not change.

### Where the generator knows it

`VerA/src/backend/codegen.zig`, `Gen.patRow`. Every site that emits a
`res[...]` write already calls it — `stamp()`, the indirect/nullor row, the
signal-flow row, both potential-branch rows, `emitSwitchRow`'s four arms and
the port-probe row. It is the single choke point, so the predicate is one `|=`
beside the one that already accumulates the column mask:

```zig
fn patRow(self: *Gen, node: u16, bits: u64) void {
    if (node == Lower.ground) return;
    if (self.pat[@intFromBool(self.pat_react)].len == 0) return;
    self.pat[@intFromBool(self.pat_react)][node] |= bits;
    self.rows[@intFromBool(self.pat_react)] |= uBit(node);   // <- new
}
```

`emitPattern` emits both masks after the dispatchers, next to
`jac_pattern`/`q_pattern`. The over-approximation direction is preserved by
construction: a `collapse_applied` build skips some emitted rows at comptime and
still declares them written, which costs a stamp that happens to be zero.

## Why it cannot be derived on the host — the invariant

`jac_pattern` and `q_pattern` answer for the **derivative**. VerA builds them by
ORing `unknownDeps(value)` into the row at every write, so a term whose value
depends on no unknown ORs *zero* into the column mask **while still writing the
row**. "No live columns" and "row is identically zero" are different statements,
and only the generator can tell them apart.

`isource` ships exactly that shape:

```
pub const jac_pattern = [n_u]u64{ 0x0, 0x0 };   // no unknown in `dc`
pub const jac_rows: u64 = 0x3;                  // both rows written
```

A host that read the clear pattern row as "identically zero" would delete every
independent current source in the netlist. On the reactive half the same mistake
is quieter and worse: a `ddt()` of something varying in `t` and not in `x` would
leave the per-state `q_tape` entry frozen at zero for a live state, and
`stepBound` would drop a real LTE bound with no error, no NaN and no diff — just
timesteps that are too long.

### The guards

Three, in the two places the mistake can be made.

1. **`tests/analyses.zig` — "written rows: an empty jac_pattern does not delete
   the current source".** `td.I` is `isource` in miniature: `jac_pattern =
   {0,0}`, `jac_rows = 0b11`, `eval` stamping a DC current into both rows.
   Asserts `ckt.rhs[n1] == -i_dc` **exactly** after a bare `ckt.eval(x, 0)`, and
   then that the DC solve lands on `i*R`. A dropped row leaves the deck
   converging happily at 0 V, which is why the plane assertion is there and not
   only the solve.
   Result: passes; deliberately breaking the gate to `jac_pat[ru] != 0` fails it
   on the first assertion.

2. **`tests/analyses.zig` — "written rows: a ddt of time alone keeps its charge
   row and its q_tape".** `td.Qt` has `q(x, t) = k·t²` with `dq/dx ≡ 0`, so
   `q_pattern = {0,0}` and `q_rows = 0b11`; `eval` writes nothing at all
   (`jac_rows = 0`), which also exercises the skip path. Asserts, after
   `ckt.eval(x, 2.0)`: `q_vec[n1] == -4.0` exactly, and `snapshotQTape()`
   returning exactly `{4.0, -4.0}` — the tape being the input `stepBound`
   reduces over. Then a transient to 1 ms, where `i = d/dt(k·t²) = 2·k·t` and
   `v = 2·k·t·R` must reach 2 V; a dropped row gives 0 V for the whole run.
   `t²` and not `t` on purpose: a quadratic charge has a nonzero second divided
   difference, so this state carries a real LTE bound rather than a degenerate
   one. (That the bound is then *used* is already pinned by
   `tran.zig:886 "stepBound: per-state min survives what the summed row
   cancels"`.)
   Result: passes.

   Note: hand-written test devices bypass `contract.validate` entirely — espice
   only calls `contract.validateHost(VpiHost, D)` — so these two devices are
   also the check that the host reads the declaration rather than the pattern.
   Generated devices get the same question asked from the other side by (3).

3. **`VerA/src/backend/tb.zig` — `rowAssert`, in the generated testbench.** The
   companion to `patAssert`: for every row NOT in `jac_rows`/`q_rows`, the
   residual VALUE (not the derivative) must be `0.0` at the sampled bias. This
   is what fails if codegen ever grows a `res[ru] = ...` that does not go
   through `patRow`.

Plus `contract.checkRowMask` (`VerA/tools/contract.zig`), which enforces the
containment that IS sound — every row with a live pattern column must be a
written row — and refuses a mask with no residual to describe, a non-`u64`
mask, or `|U| > 64`. It is factored as `rowMaskError` returning the message so
the rule is unit-testable; `contract.zig`'s new test pins both directions,
including that `isource`'s empty-pattern/written-row shape stays legal.

`jac_rows`/`q_rows` were added to `allowed_pub_decls`, and `MockAll` now
declares all four of `jac_pattern`, `q_pattern`, `jac_rows`, `q_rows`. That last
part fixes a pre-existing break: on `a19b6fb`, `zig build test-contract` failed
to compile because `q_pattern` was allowlisted and `MockAll` did not declare it.

## What the host does with it

`ARPice/src/devices/engine.zig`:

- `writtenRows(D, name)` — the comptime `[n_u]bool`, with the whole invariant in
  its doc comment and an all-true fallback when the decl is absent.
- `evalRange` gates both row loops: `if (comptime jac_row[ru])` on the resistive
  pass, `if (comptime q_row[ru])` on the reactive one.
- `evalQRange` (the post-accept charge re-read) gates on the same `q_row`, and
  it must be the same one or that pass stops being bit-for-bit what a full
  `evalRange` leaves behind.
- `Sink.tryCached` gates its replay identically, so the (currently unreachable)
  dedup cache cannot drift from the pass it replays.

Two things make the skip bit-identical rather than merely close:

- **The planes.** `rhs`/`q_vec`/`g_vals`/`c_vals` are `@memset` to `+0.0` at the
  start of every `eval` and only ever grown by `+=`. An accumulator seeded at
  `+0.0` can never become `-0.0` under addition, so a skipped `+= 0.0` cannot
  flip a sign bit. The GPU staging cells and ParEval's per-lane slabs are zeroed
  per pass with the same contract (`Sink.add`'s comment already says so), and
  ParEval's window comes from `tapeBounds`, which reads the tapes, not what was
  written.
- **`q_tape`.** `scatterQ` *assigns* rather than accumulates, so a skipped row
  would be a stale read if anything else could have written it. Nothing can:
  `ProtoStore.finalize` `@memset`s the tape to 0 once at allocation and
  `scatterQ` is its only writer, so a row nothing writes reads `+0.0` forever —
  which is exactly the value the skipped store would have put there.

## Measured

Devices regenerate wholesale on a VerA change, so the first thing checked was
that regeneration is physics-neutral: all 39 generated devices were diffed
against their pre-change copies in `.zig-cache`, and the **only** difference is
the two new declarations and their doc comments. mos1's 2000-line kernel is
byte-identical.

| device | `jac_rows` | dead res rows | `q_rows` | dead q rows |
|---|---|---:|---|---:|
| mos1 / mos2 / mos3 / mos6 / mos9 / bsim1 / bsim3 | `0xfd` | 1 of 8 | `0x3a` | 4 of 8 |
| capacitor | `0x0` | **2 of 2** | `0x3` | 0 of 2 |

The capacitor is the shape the pattern could never have expressed: `eval`
returns all zeros, so its whole resistive stamp is dead, and both benchmark
decks are full of them.

### Per-instance

Iterate counts from `ZP_TRAN_STATS=1` (already in the tree, `tran.zig:439`):

| deck | instances | `nr_iters` | `accepted` | skipped row-bodies |
|---|---|---:|---:|---:|
| pi100 | 200 mos1, 100 cap, 2 vsrc | 1352 | 595 | 2,098,400 |
| mos6_inverter | 80 mos6, 16 cap, 2 vsrc | 884 | 316 | 483,008 |
| rc_chain_500 | 500 cap, 500 res, 1 vsrc | 544 | 271 | 544,000 |

("Skipped row-bodies" = `nr_iters × Σ dead rows` from `evalRange` plus
`accepted × Σ dead q rows` from `evalQRange`. It excludes the OP solve's own
iterates, which nothing prints, so every rate below is a slight over-estimate.)

| deck | Ir per skipped row-body |
|---|---:|
| rc_chain_500 — pure RESISTIVE row | **3.02** |
| mos6_inverter — blended | 4.92 |
| pi100 — blended | 6.54 |

**Per instance, the number item 4 predicted at 22 Ir:**

- mos1 skips 5 row-bodies per Newton stamp (1 resistive + 4 reactive) and 4 more
  in the post-accept charge pass → **32.7 Ir per mos1 per Newton iterate** on
  pi100.
- mos6 skips the same 5 + 4 → **24.6 Ir per mos6 per Newton iterate**.
- Against the stamp's 195 Ir/instance, that is **17%** of the mos1 stamp deleted;
  its scattered RMW count goes 61 → 52 (−1 rhs, −4 `q_vec`, −4 `q_tape`).
- The capacitor loses both of its resistive rows outright: 10 RMWs → 8.

The rate is NOT transferable between decks (3.02 / 4.92 / 6.54), so treat the
per-instance figures as per-deck. Feeding the directly measured 3.02 Ir
resistive row into mos6_inverter implies ≈5.4 Ir per reactive row-body; that
model then predicts 10.1M for pi100 against 13.7M measured. The extra ~3.7M is a
codegen knock-on inside the mos1 kernel — a shorter stamp loop relieves the
register pressure the two rejected reshapes in item 7 both ran into — which is
real and welcome but is not "the stamp".

### The guards were shown to have teeth

`writtenRows` was temporarily replaced with the bug — derive the predicate from
`rowPattern(D, "jac_pattern"/"q_pattern")[ru] != 0` — and the suite rebuilt:

```
error: 'written rows: an empty jac_pattern does not delete the current source'
       expected -0.0010000000474974513, found 0
error: 'written rows: a ddt of time alone keeps its charge row and its q_tape'
       expected -4, found 0
Build Summary: 406/408 tests passed (2 failed)
```

Exactly two failures out of 408. **Nothing else in the entire suite noticed** —
which is the whole argument for writing them.

## Left on the table

- `stepBound` still reduces over the dead `q_tape` rows — 4 of every mos1's 8,
  800 of pi100's 1800 entries. They are hard `+0.0` and their bound is
  `trtol·tol/abstol` ≈ 10⁵ s, so they never bind; dropping them from the tape
  would be a real 3.3%-pass saving but it is NOT bit-identical by construction,
  only by that argument. Wants its own change and its own proof.
- The tapes (`rhs_idx`, `slots`) are still built for dead rows. Setup cost, not
  measured, not worth it.
