# `vera --check` hang — investigation, 2026-09-10

Three `zig build-obj -fno-emit-bin` processes (mes, bsim3, hfet2) were found at
99% CPU for 82 minutes, orphaned, with the parent `zig build` idle. This is the
write-up of what they actually were.

**Answer up front: it is the invocation, not sema.** There is no pathological
construct in those three devices and no sema pathology anywhere in the catalog.
The command that ran is a no-op that cannot take measurable time — and, for the
same reason, has never type-checked anything. Both halves of that are defects.

---

## 1. The reproduction, and its failure

The command under investigation, from `../VerA/src/cli.zig` `typeCheck()`:

```
zig build-obj -fno-emit-bin --dep contract \
  -Mroot=.zig-cache/vera-check/<stem>.device.zig \
  -Mcontract=../VerA/tools/contract.zig --cache-dir .zig-cache
```

Every measurement below is Zig 0.16.0
(`/nix/store/n1hqsn4a4yfmipzyk2byavvx4ccx6ccr-zig-0.16.0`), `/usr/bin/time -v`,
`timeout 300` on every run.

**It does not hang. It cannot.** All 39 generated devices, run cold against a
freshly created private cache directory:

| device | source | wall | peak RSS |
|---|---|---|---|
| hisimhv_va | 2.1 MB | 0.14 s | 101 MB |
| hisim2_va | 1.5 MB | 0.13 s | 101 MB |
| bsim4va | 831 KB | 0.10 s | 109 MB |
| bsimsoi_va | 617 KB | 0.09 s | 101 MB |
| **bsim3** | **110 KB** | **0.05 s** | **102 MB** |
| **hfet2** | **52 KB** | **0.04 s** | **101 MB** |
| **mes** | **45 KB** | **0.05 s** | **101 MB** |
| capacitor (control) | 20 KB | 0.04 s | 101 MB |

Nothing in the catalog exceeds 0.14 s. There is no contrast between the three
suspects and the control, because there is nothing happening in either.

Variations tried, all identical to within noise:

- shared `--cache-dir .zig-cache` vs private `/tmp/vc-cache` — **0.04 s both.**
  Cache-lock contention is ruled out; it would also present as 0% CPU, not 99%.
- warm cache hit vs forced miss (copy the root to a new name so the manifest
  hash changes) — **0.04 s both.** The fast times are not cache hits.
- peak RSS is flat at ~101 MB for a 20 KB device and a 2.1 MB device alike.
  There is no sema memory explosion and nothing that could push this box
  (31 GB, 1 GB swap in use) into swap.
- the Aug-18 agent-worktree copies of these same devices, generated by an older
  VerA and textually different — **0.05 s.** Not a regression in current codegen.

## 2. Why it is so fast: the check checks nothing

`-fno-emit-bin` analyses **lazily**. With no binary requested, nothing is a
root, so only what is unconditionally reachable gets sema'd. Probed directly:

| root file | caught? |
|---|---|
| syntax error | yes — parse always runs |
| `comptime { @compileError("SEMA-RAN"); }` | yes — top-level comptime blocks always run |
| `pub export fn f() u32 { const x: u32 = "str"; ... }` | yes — `export` is a root |
| `pub fn f() u32 { const x: u32 = "str"; ... }` | **no — exit 0** |
| `const x: u8 = "not a u8";` at top level | **no — exit 0** |

A generated device has **no `export` and no `test`**. Its only eager work is
two comptime blocks: `contract.checkScalar(R)` and `contract.validate(Self)`.
And `validate` is pure reflection — it says so in its own comment at
`../VerA/tools/contract.zig:1080`:

> `ret` only names the expected result in the complaint — **a generic return
> cannot be checked without instantiating.**

`validatePhysicsFn` therefore checks only that `eval` is a 5-parameter function
whose first parameter is `type`. It never instantiates it. So no `eval`, `q`,
`evalQ`, `precompute`, `collapse` or `updateState` body has ever been analysed
by `--check`.

**Demonstrated:** a deliberate `const zzz: u32 = "DELIBERATE TYPE ERROR";`
injected into the first line of `mes`'s `eval` body:

```
$ zig build-obj -fno-emit-bin ... -Mroot=/tmp/vc-probe/mes_broken.device.zig ...
rc=0        # zero bytes of stderr
```

`--check` passes a device whose `eval` does not compile. That is the real
defect this investigation found, and it is why the flag has never once caught
the codegen bug it was added for (`build.zig:104`: "a bad lowering names the
source instead of surfacing inside a cache file").

## 3. What the three devices share: nothing

The trio is not a content class. Ruled out by inspection and by measurement:

- none of the 39 devices contains an `inline for`, an `inline while`, or a
  `@Vector` at all. Zero, catalog-wide.
- mes, hfet2, bsim3 and bsim4va all emit exactly the same two comptime blocks.
  bsim4va — 800× the size — takes 0.10 s.
- there is no list in `build.zig` that selects these three. The only per-model
  branches are `-Djac-f32` (empty by default) and the GPU size thresholds, and
  the size thresholds group mes/hfet2/bsim3 with ~30 other devices, not with
  each other.

The trio's real origin is **build parallelism**. `typeCheck` writes
`.zig-cache/vera-check/<stem>.device.zig` before spawning, so a partial
`vera-check` directory is a record of which devices were in flight when a build
was interrupted. The Aug-18 agent worktree stopped with a similar small set.
Whichever 3–4 Run steps the build runner happened to have live at the moment of
the wedge are the ones you find. mes/bsim3/hfet2 is a snapshot of a thread
pool, not a property of MESFETs and BSIM3.

(`../wt-mem/ARPice/.zig-cache/vera-check` looked like corroborating evidence and
is not: it holds all 39 files with mtimes identical to the main tree's to the
nanosecond and different inodes — a `cp -a` snapshot taken at 13:55.)

## 4. Was it even this command?

`-fno-emit-bin` occurs exactly once in the entire build graph — ARPice
`build.zig`, VerA `src/`, gompute, and Zig 0.16's own `std/Build/` were all
grepped. Zig's build runner never passes it. So the processes were `typeCheck`
children.

Two mechanisms that would explain 99% CPU were tested and are dead:

- **progress-pipe fd inheritance** (`ZIG_PROGRESS` leaking from `zig build`
  into a grandchild compiler). `ZIG_PROGRESS` does not exist in Zig 0.16's
  stdlib at all; setting it to a bogus fd changes nothing (0.05 s, rc=0).
- **shared-cache lock contention.** Private cache dir is exactly as fast, and a
  contended `flock` sleeps rather than spins.

What remains is unattributable from here: the processes are gone, and the
command they were running provably does ~40 ms of work on every input that
exists on disk. Machine state at the time (several concurrent `zig build`s
across five worktrees) is the most likely contributor, and it is not something
the generated code can be blamed for or fixed in.

That is precisely why the bound below is the right response regardless: a build
step that can hang forever with no diagnostic is a defect **independent of its
root cause**, and it is the reason an 82-minute orphan was possible at all.

## 5. Minimal reproducer

**There is none, and that is the finding.** The hang does not reproduce from
any generated device text present in any worktree on this machine, under any
cache configuration. What does reproduce, deterministically, is the vacuous
check in §2:

```sh
cp .zig-cache/vera-check/mes.device.zig /tmp/broken.zig
# insert `const z: u32 = "x"; _ = z;` as the first line of eval()'s body
zig build-obj -fno-emit-bin --dep contract -Mroot=/tmp/broken.zig \
    -Mcontract=../VerA/tools/contract.zig --cache-dir /tmp/c   # -> rc=0
```

## 6. Fixes

### (a) Shipped — bound the check. `../VerA/src/cli.zig`

`typeCheck()` had no timeout. It now spawns a `killAfter` watchdog via
`io.concurrent` with a 120 s budget, kills the child if it expires, and fails
the check naming the device, the budget and the artifact path:

```
error: src/devices/models/mes.va: type check did not finish in 120s and was
killed. The generated Zig is at .zig-cache/vera-check/mes.device.zig; run the
`zig build-obj` from typeCheck() by hand to see where it sticks.
```

Verified both ways with the real binary: budget 0 produces the message above
and exit 1; budget 120 leaves the normal path at 0.09 s end to end.

Two details worth keeping:

- `io.concurrent`, not `io.async` — `async` may legally run the watchdog inline
  on the calling thread, which would sleep out the budget before the child was
  ever read. An `Io` without concurrency falls back to the old unbounded wait
  rather than a wrong one.
- the watchdog is cancelled **before** `child.wait` reaps. After the reap the
  pid belongs to whoever the OS hands it to next. `Child.kill` also reaps what
  it kills, so the timed-out path must not `wait` again — that is an assert in
  `Child.wait`, and hitting it panics (confirmed with a standalone probe).

120 s is three orders of magnitude over the measured 0.03–0.28 s. Anything that
trips it is wedged, not slow.

### (b) Recommended — make `--check` actually check

The check is worth roughly its runtime today, which is zero. Forcing `eval` to
be a root fixes it. Appending this to the copy `typeCheck` writes into
`.zig-cache/vera-check/` (not to the shipped device — it is check-only scaffolding)
is enough:

```zig
export fn zzz_force_eval() void {
    var mo: Model = .{};
    var ins: Instance = .{};
    const x: [n_u]R = @splat(R{ .v = 0.0 });
    const r = eval(R, x, &mo, &ins, 0.0);
    for (r) |e| std.mem.doNotOptimizeAway(e.v);
}
```

`R` is the device's own scalar (already present for `checkScalar`), and `Model`
/ `Instance` are fully defaulted by contract, so `.{}` is valid.

Measured cost of doing this, per device, cold cache:

| device | forced-eval wall | peak RSS |
|---|---|---|
| hisimhv_va | 0.28 s | ~120 MB |
| hisim2_va | 0.26 s | — |
| bsim4va | 0.24 s | 120 MB |
| bsim3 | 0.21 s | 111 MB |
| mos6 | 0.21 s | 111 MB |
| hfet2 | 0.19 s | 111 MB |

**Whole catalog: about 8 seconds**, and it turns a class of codegen bug that
currently surfaces 35 minutes later inside `build-exe` into a 0.2 s failure
that names the `.va`. It also confirms there is no sema pathology to find:
even with every `eval` body fully analysed, the three suspects are ordinary.

Not shipped here because it is a behaviour change that can newly fail the build
for anyone whose device has a latent body error, and that deserves its own
change with the fallout handled. (The stub above compiles clean for all 25
devices where its `R`-shaped scalar applies; the 6 linear devices need a
slightly different forcing shape.)

### (c) Also noted — `--check` drives the wrong `zig`

`typeCheck` spawns `zig_exe`, which defaults to `"zig"` from `PATH`
(`cli.zig:155`). `build.zig:116` never passes `--zig`, so the check runs
whatever compiler `PATH` supplies rather than `b.graph.zig_exe` — the one
running the build. Same version here by luck. One argument fixes it.

No skip list was needed; there is nothing to skip.
