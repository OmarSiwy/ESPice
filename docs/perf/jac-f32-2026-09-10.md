# `jac_f32` on the CPU — measured, 2026-09-10

`docs/perf/remaining-2026-09-10.md` §9 and `todo.md` logged `-Djac-f32` as
"implemented end to end, never measured on CPU". This puts numbers on it.

**Verdict: keep for `mos1` and `mos6`, drop for `bsim4va` and `diode`, and
gate it behind a robustness caveat — one MOS1 fixture (`ngspice/mosmem`)
regresses 13.7% because the f32 Jacobian breaks plain Newton on its operating
point and forces the whole gmin ladder.** Nothing failed to converge and no
accuracy gate moved.

---

## Methodology — two real builds, no ablation

Hazard 5 of the handoff doc says the "gate a pass to run twice and difference"
trick gives the opposite sign and 14× the magnitude on codegen questions. This
is a codegen question, so both sides are real builds from the same tree
(`jac-f32` @ `446268a`), differing only in the build flag:

```
zig build -Dgpu=false                                      -p out-f64
zig build -Dgpu=false -Djac-f32=mos1,mos6,bsim4va,diode    -p out-f32
```

`-Dgpu=false` on both (§13: the CPU-measurement build; the NVPTX/AMDGCN device
kernels are separate compilations and cannot reach a CPU Ir count). Verified
the flag landed: exactly one generated `mos1.zig`/`mos6.zig`/`bsim4va.zig`/
`diode.zig` in the cache carries `pub const jac_f32 = true`, and the two
generated variants of a model differ **only** by that decl plus its doc
comment — the flag is a pure host-side switch on `engine.jacFloat`.
`bjt`/`mos3` (unlisted controls) have no such decl in any variant.

Metrics:

- **Ir** — `valgrind --tool=callgrind`, contention-immune (other agents are
  building on this machine). Every run's exit status and raw file were checked;
  no run SIGILLed or aborted early.
- **Per-eval Ir** — `callgrind_annotate` ranks functions by hex address (the
  binary is `-fstrip`; `-Ddebug-info=true` SEGVs the compiler). On the
  MOS/BSIM decks the rank-1 function is the device `evalQ` at 49–59% of the
  run, so its self cost divided by (NR iterations × instances) is the
  per-instance-eval cost with no ablation and no symbol table. On the diode
  decks the kernel is not rank-1; it is identified instead by being the *same*
  address in both diode decks (`0x1f5fe50` f64 / `0x1f5df50` f32) and the only
  function in either whose cost moves at all — every other top-8 entry is
  Ir-identical between builds.
- **NR iterations** — `ZP_TRAN_STATS=1` for the transient counters, and
  `ZP_OPDBG=1 | grep -c "newton it="` as a universal counter that also covers
  `.op`/`.dc` and the operating-point ladder. Cross-checked on pi100: 1358
  `newton it=` lines vs `nr_iters=1352` — the 6 extra are the OP solve, which
  `tran-stats` does not count. `ZP_OPDBG` is a print-only path; the numerics
  are unchanged, and it is never enabled inside a callgrind run.
- **Accuracy** — f32 raw vs f64 raw with the bench runner's own rule
  (`runner.zig comparePlots`: per-variable error normalised by
  `max(peak, span, 1)`, pass at RMS ≤ 1e-3 and max ≤ 1e-2), plus a full
  `bench-runner` pass of each build against pinned ngspice 44.2
  (`/nix/store/bywwgg84…-ngspice-44.2`).

sweep, and both give the same ratio, which is the point.

### `parallel_inverters_100` — the gate deck

- Whole run **0.9362 (−6.38%)**: 466,359,299 → 436,603,086 Ir.
- Iteration count **did not rise**: 1352 → 1349 transient NR iterates,
  **613 → 613 attempts, 595 → 595 accepted points**, identical rejection
  breakdown (`rej[newton=0 lte=18 state=0]`), identical `avg_dt`. The OP solve
  went 6 → 7 iterates. Total 1358 → 1356.
- Per-NR-iterate whole-run cost 343,416 → 321,979 Ir (0.9376).
- The mos1 `evalQ` itself: 259,390,832 (55.6% of the run) → 234,528,036
  (53.7%), i.e. **0.9041**, or 955.0 → 864.8 Ir per MOSFET per NR iterate.
- `parallel_inverters_500` reproduces it independently at 5× the instance
  count: whole run 0.9352, kernel 0.9048, per-eval 954.9 → 864.7.

So both sides of the trade are on the table: per-iterate cost fell 6.2–6.5%
and the iteration count fell by 3 out of 1352. It is a clean net win on this
deck.

The §9 estimate was 0.77 on the AD vector arithmetic. 0.90 on the whole kernel
is consistent — the `Dual` value half is f64 either way, the transcendentals
are f64 libcalls, and the stamp widens back to f64 at `grad()`/`ddxAt`, so only
the derivative-vector instructions move.

## Which models it helps, and why: it is `n_u`, not model size

`-Djac-f32` takes a comma-separated list of model **file stems**
(`build.zig:18,107`, `inCsv`). The win tracks the device's unknown count
`n_u = @typeInfo(D.U).@"enum".fields.len`, which sets the `@Vector(n_u, F)`
width in `engine.DualFor` — not the size of the model:

| model | `n_u` | f64 ymm-equivalents | f32 ymm-equivalents | measured kernel |
|---|---:|---|---|---:|
| `diode` | 4 | 1 (ymm) | 1 (xmm) | **+4.0% / +5.0%** |
| `mos1` | 8 | 2 | 1 | **−9.6%** |
| `mos6` | 8 | 2 | 1 | **−9.9%** |
| `bsim4va` | 18 | 5 + tail | 3 + tail | **−0.04%** |

(The register columns are `ceil(n_u/4)` and `ceil(n_u/8)` on AVX2, i.e.
arithmetic on the width — the measured column is the evidence, the register
count is the account of it, not a disassembly.)

- **`n_u = 8` is the sweet spot** and the only one. It is exactly the case §9
  costed: 2 AVX2 registers collapse to 1. mos1 and mos6 both have
  `U = {d,g,s,b,di,si,flow(d,di),flow(s,si)}`.
- **`n_u = 4` (diode) is already one vector instruction in f64**, which is the
  same settled result as the retired derivative-narrowing experiment ("on AVX2
  every width ≤ 4 is ONE vector instruction, so narrowing … saves zero"). Here
  it is worse than zero: the diode kernel is **4.0% (rectifier) and 5.0%
  (diode_iv_sweep) slower**, because nothing is saved and the `@floatCast`
  widening at the scatter is added. Whole-run is −0.4%/−0.5%, i.e. inside the
  noise of an unrelated code-layout shift.
- **`n_u = 18` (bsim4va) gets exactly nothing.** 81,442,455 → 81,408,595 Ir in
  the kernel (−0.04%), and the rank-2 through rank-7 functions are Ir-identical
  to the digit. The f32 Jacobian *is* live — the Newton traces differ in 58 of
  542 lines — it simply buys no instructions at a non-power-of-two width whose
  legalisation carries shuffle tails either way. This is the same mechanism
  that made the k=6 narrowing experiment a 21% loss. bsim4 is the biggest
  model in the tree and the AD layer is *not* the reason it is expensive: its
  eval is 18,493 Ir per instance per iterate against mos1's 955, and none of
  the difference is in the derivative vector.

Corollary for §11: item 9 was listed as the prerequisite for re-admitting
bsim4-class models to the GPU. On the CPU it does not touch bsim4 at all. That
does not settle the GPU question (a 64:1 f64:f32 rate ratio is a different
argument, and `gpu-layout-eval` owns it), but the CPU half of the prerequisite
is not there.

Non-listed models are unaffected: `bjt` and `mos3` generate without the decl,
and every fixture in the sweep below that differs between the two builds
contains at least one mos1, mos6, bsim4va or diode instance. The converse is
not true — 22 fixtures that *do* contain a listed model are still bit-identical
(`devices/mos1_output`, `sweep/nmos_wl_opt`, `power/buck_open`, …), because a
well-conditioned Newton lands on the same f64 double from either Jacobian.

## Accuracy — the "cost is iterations, not the answer" hypothesis holds

Tested, not assumed. 57 fixtures covering every mos1, mos6, bsim4 and diode
deck in the tree plus `convergence/*` and `adversarial/*`, f32 raw against f64
raw under the suite's own rule (RMS ≤ 1e-3, max ≤ 1e-2, per variable,
normalised by `max(peak, span, 1)`).

**Every deck passes. 22 of 57 are bit-identical.** The largest deltas:

| deck | max rel | RMS rel | note |
|---|---:|---:|---|
| `tline/ltra1_1_line` | 9.98e-4 | 2.22e-4 | mos1 driver into an LTRA line |
| `tline/txl1_1_line` | 9.61e-4 | 2.20e-4 | same |
| `ngspice/mosmem` | 7.72e-4 | 2.87e-4 | latch; grid moved 148 → 151 points |
| `tran/fourbitadder` | 5.76e-6 | 3.49e-6 | |
| `sweep/opamp_wl_1000` | 3.36e-7 | 1.74e-7 | AC |
| `scaling/parallel_inverters_100` | 3.11e-7 | 1.85e-8 | |
| `devices/mos6_inverter` | 4.35e-10 | 2.88e-11 | |

The three worst are all at ~2–3e-4 RMS, i.e. **a quarter of the pass budget
consumed against a different build of the same simulator**. That is far above
round-off and is the accepted-timestep grid moving, not the physics: the three
are the decks whose trajectories are steep (transmission-line wavefront,
latch), so a shifted LTE decision reads as a large pointwise error. The
comparison above deliberately does *not* apply the runner's edge-window
relaxation, because on a build-vs-build comparison that would hide exactly the
thing worth seeing.

Against ngspice 44.2 (pinned store path, full `bench-runner` pass of each
build, 196 comparable fixtures): the PASS/FAIL verdict is **unchanged on every
one**. Only 8 fixtures' error numbers move at all, and in six of the eight the
f32 build is *closer* to ngspice than the f64 build — `ngspice/mosmem` RMS
2.57e-4 → 1.03e-4, `tline/ltra1_1_line` 3.63e-4 → 2.87e-4,
`tran/fourbitadder` 8.41e-6 → 6.41e-6. That is not an improvement, it is
confirmation that the movement is the timestep grid, which the reference
comparison's interpolation is free to land either side of.

Six fixtures FAIL against ngspice in **both** builds with byte-identical
numbers, i.e. pre-existing and untouched: `devices/bsim4` (1.69e-3),
`devices/hfet_inverter` (3.18e-2), `devices/mos6_inverter` (3.27e-2),
`ensemble/pvt_corners` (9.07e-2), `ngspice/mosamp` (2.12e-2),
`scaling/parallel_inverters_2000` (1.17e-2).

Mechanically this is what the design says should happen. The residual half of
`Dual` is f64 unconditionally, `ddxAt`/`grad()` widen back to f64 before the
scatter, and `direct.Solver` is `SolverT(f64)`, so the converged point is still
the root of an f64 residual. `layoutHash`, the scatter tapes and `jac_pattern`
do not move (they are keyed on types that do not contain `F`), and the
device-test suite's `engine.test."Dual: an f32 Jacobian leaves the residual
bit-identical"` pins the value half directly.

## Convergence robustness — one real regression

`convergence/*` and `adversarial/*` were run on both builds. **All six are
bit-identical or pass, none regressed** — but they are also all null tests for
this change: `high_gain_fb` and `schmitt` are VCVS-only, `near_singular`,
`tiny_resistor` and `extreme_values` are R/C only, and only `diode_bridge`
contains a nonlinear device the flag touches (12 NR iterations in both builds,
max 4.08e-11). No MOSFET appears in any of them. The stiff-deck coverage this
change actually needs is not in those two directories.

Looking instead at every mos1/mos6/bsim4/diode deck, five change their
iteration count by more than ±1:

| deck | NR f64 | NR f32 | Δ | whole-run Ir |
|---|---:|---:|---:|---|
| `ngspice/mosmem` | 380 | **481** | **+26.6%** | **+13.73%** |
| `devices/diode_recombination` | 963 | 1078 | +11.9% | — |
| `devices/diode_temp` | 1906 | 1941 | +1.8% | — |
| `devices/diode_iv_sweep` | 2510 | 2525 | +0.6% | −0.54% |
| `devices/diode_high_injection` | 904 | 914 | +1.1% | — |

### `ngspice/mosmem` — the counter-example

A MOS1 cross-coupled memory cell. Under f64 the operating point converges on
the first rung:

```
ladder: plain conv=true                (f64 — 50 NR iterates, done)
```

Under f32 plain Newton **fails**, burning `itl1` and falling through to the
whole gmin-stepping ladder:

```
ladder: plain conv=false               (f32 — ~102 iterates, gave up)
ladder: gmin=1.000e-3 conv=true it=9
ladder: gmin=1.000e-4 conv=true it=3
…  11 rungs, 42 more iterates
```

Operating point 50 → 144 NR iterates. The transient that follows costs only
+7 (330 → 337; 147 → 150 accepted points). Per-iterate cost on this deck fell
*more* than on pi100 (Ir/NR ratio 0.8985 — it is more kernel-bound), and it
still lost: **16,732,379 → 19,029,570 Ir, +13.73%**.

The answer is fine — the ladder recovers and the deck passes accuracy at max
7.72e-4 — but this is precisely the failure mode §9 predicted and did not
price. It is a latch: near the metastable point the Jacobian's conditioning is
what decides whether plain Newton finds the basin, and 7 digits is not enough.
`mosmem` is the only deck in the tree that flips a `plain conv=true` into a
`plain conv=false`; a scan of all 57 `ZP_OPDBG` traces found no other
ladder-path change except on the two decks that already fail (below).

### Pre-existing failures, unchanged

`scaling/inverter_chain_256` and `scaling/inverter_chain_1k` exit 1 on **both**
builds with byte-identical telemetry — `DT UNDERFLOW (newton) at
t=4.976035e-11 dt=9.537e-19 accepted=16 attempts=62 nr_iters=514`. Not caused
by, and not fixed by, this flag.

## Iterative refinement — no interaction, and it could not help

§9 asked whether `direct.zig`'s `iter_refine_steps`/`rbuf` makes this the
classic mixed-precision solver (cheap f32 factorisation + one f64 refinement
step). **It does not, on three independent grounds:**

1. **The LU never sees f32.** `Dual.ddxAt` and `Dual.grad` widen the derivative
   back to f64 before the scatter (`engine.zig:118-129` names the three widening
   sites), the solver's `g_vals` is `[]f64`, and `pub const Solver =
   SolverT(f64)` is the only instantiation any analysis builds. `SolverT(f32)`,
   `SparseLu(f32)`, `TriDiag(f32)`, `DenseLu(f32)` and `FreqSolverT(f32)` all
   exist and are exercised **only by unit tests**. `jac_f32` saves instructions
   inside the device kernel's AD arithmetic; the factorisation cost is
   identical in both builds.
2. **Refinement is off everywhere.** `iter_refine_steps` defaults to 0 and the
   only non-zero assignment in the tree is `direct.zig:292`, a unit test.
3. **It would not recover anything if it were on.** Iterative refinement
   corrects a *solve* against the stored `A`. Here `A` itself is the perturbed
   quantity — this is inexact Newton, not an inexact solve — so refining
   converges harder onto the perturbed Jacobian's step, which is not the
   defect. The construction that already handles it is the one in place: the
   residual stays f64, so the fixed point is exact regardless of the Jacobian.
   That is why the accuracy result above is what it is, and why the entire cost
   shows up as iteration count.

## Build cost

`-Djac-f32=<stem>` does **not** rerun VerA in any meaningful sense: the vera
binary is unchanged and cached, and the flag only adds `--jac-f32` to that one
model's existing codegen invocation. It does force a full ARPice `build-exe`
recompile, because all 38 generated models are `-M` modules of one
`build-exe` and Zig caches that compilation as a unit (§13). Measured with a
warm cache and heavy machine contention: **16m55s** for the f64 build,
**14m45s** for the four-model f32 build, both `-Dgpu=false`. Adding models to
the list is free — one rebuild covers any number of stems, which is how mos1,
mos6, bsim4va and diode were measured against a single baseline.

`zig build test -Dgpu=false` **exits 0** on the tree as committed (this commit
adds documentation only — no source changed). The device-test step still
renders the §13 stderr gate (`failed command: …/test --listen=-`, from two
`devices:` warnings on stderr) without failing the aggregate; run standalone
that binary is **11/11, exit 0**, including
`engine.test."Dual: an f32 Jacobian leaves the residual bit-identical"`, which
is the unit-level version of the accuracy result above.

## Recommendation

- **`mos1`: keep**, with the caveat below. −6.4% on both gate-adjacent scaling
  decks, no iteration cost, no accuracy movement.
- **`mos6`: keep.** −5.1% on `devices/mos6_inverter`, iteration count
  identical to the iterate. That deck is the only remaining loss against
  ngspice's from-source build (1.031 in the handoff table, i.e. 3% behind);
  1.031 × 0.9489 = **0.978**, so this alone would flip it to a 2% win. Worth
  re-measuring against a rebuilt from-source ngspice before quoting (hazard 4).
- **`bsim4va`: drop.** Zero, measured three ways.
- **`diode`: drop.** The kernel is 4–5% *slower*.
- **Not yet default.** `ngspice/mosmem` costs 13.7% because the flag broke
  plain Newton on a latch, and one deck out of 57 is thin evidence either way.
  The honest shipping form is `-Djac-f32=mos1,mos6` measured on a wider stiff
  MOS corpus first: the tree has no MOSFET deck under `convergence/` or
  `adversarial/`, which is why the only counter-example turned up by accident
  in `ngspice/`. Adding a MOS latch and a MOS Schmitt to `convergence/` is the
  cheap prerequisite to making this a default.
- If it is made a default, `op.zig`'s ladder already contains the recovery
  (mosmem lost time, not correctness). A cheaper alternative would be to solve
  the OP in f64 and switch the transient to f32 — the flag is comptime per
  device today, so that is a real change, not a flag.

## Reproduce

```
zig build -Dgpu=false                                   -p out-f64
zig build -Dgpu=false -Djac-f32=mos1,mos6 -p out-f32
D=benchmark/fixtures/scaling/parallel_inverters_100/circuit.sp
for v in f64 f32; do
  ZP_TRAN_STATS=1 ./out-$v/bin/espice -b -r /dev/null $D
  valgrind --tool=callgrind --callgrind-out-file=cg-$v.out ./out-$v/bin/espice -b -r /dev/null $D
  callgrind_annotate --threshold=60 cg-$v.out | head -30
done
```
