# Local truncation error — the GEAR coefficient, and the per-`ddt` question

Branch `lte-fixes` off `spice-audit` (`6aa1468`). Reference C throughout is
ngspice 44.2 from source, `/tmp/ngsrc/ngspice-44.2` (same tarball as the rest
of the audit; the install prefix is
`/home/omare/Documents/Projects/Zig/ngspice-44.2-fromsource`).

Three things are settled here. Two are bugs and are fixed, one commit each.
The third is the open `todo.md` item **per-`ddt` LTE states**, and it is
answered with a measurement rather than a change: the finer index space does
not buy accuracy per step. It buys steps.

## The ngspice coefficients, verbatim

`src/spicelib/analysis/cktterr.c:24-34`:

```c
static double gearCoeff[] = {
    .5, .2222222222, .1363636364, .096, .07299270073, .05830903790
};
static double trapCoeff[] = { .5, .08333333333 };
```

selected at `:58-67` by the integration method and indexed `[CKTorder-1]`:

```c
switch(ckt->CKTintegrateMethod) {
    case GEAR:        factor = gearCoeff[ckt->CKTorder-1]; break;
    case TRAPEZOIDAL: factor = trapCoeff[ckt->CKTorder - 1]; break;
}
del = ckt->CKTtrtol * tol/MAX(ckt->CKTabstol, factor * fabs(diff[0]));
if(ckt->CKTorder == 2) del = sqrt(del);
```

(`src/xspice/mif/miftrunc.c:141-210` carries an identical pair of tables for
code models, which is a second in-tree witness to the same numbers.)

espice's order is fixed by the method — `backward_euler` is order 1,
`trapezoidal` and `gear_2` are order 2, and there is no order 3+. So the
coefficient is a function of the method alone:

| espice method | ngspice entry | value |
|---|---|---|
| `backward_euler` | `gearCoeff[0] == trapCoeff[0]` | 0.5 |
| `trapezoidal` | `trapCoeff[1]` | 1/12 = .08333333333 |
| `gear_2` | `gearCoeff[1]` | 2/9 = .2222222222 |

Order 1 is `.5` in **both** tables, which is why backward Euler could never
have been wrong, and the order-2 GEAR entry was the only one that could be.

## Defect 1 — GEAR order 2 used `trapCoeff[1]`

`tran.zig:126,148` (pre-fix) hardcoded `if (order2) 1.0/12.0 else 0.5`, with
`order2 = method != .backward_euler`. Gear shared the trapezoidal
coefficient. Because `del` goes under a square root at order 2, the bound was
`sqrt((2/9)/(1/12)) = sqrt(8/3) = 1.633x` **looser** than GEAR's own error
control asks for, on every `method=gear` deck.

**Fix.** `stepBound` takes the `Method` instead of an `order2: bool`, and
`integrator.lteCoeff(method)` holds the table. Both call sites already had a
method in hand (`eff_method` for the accept test, `options.method` for the
BE→order-2 promotion probe at `dctran.c:901-913`), so the thing that picks the
method owns the coefficient; nothing is threaded through as a flag.

Pinned by `test "lteCoeff: ngspice gearCoeff/trapCoeff tables"`.

### What it does to the corpus: nothing

Both shipping gear fixtures are **tmax-locked**:

```
vacask/mul     .options klu method=gear maxord=2   .tran 0.01u 5m 0 0.01u
vacask/graetz  .options klu method=gear maxord=2   .tran 1u   1  0 1u
```

## Defect 2 — espice's GEAR-2 was uniform-step-only

Found by defect 1, not suspected before it.

`NIcomCof` (`src/maths/ni/nicomcof.c:52-136`) builds the GEAR corrector by
solving a Vandermonde system over the **actual** step history
`CKTdeltaOld[]` — ngspice's gear-2 is a variable-step BDF2, rebuilt every
step. `NIintegrate` (`niinteg.c:41-67`) then applies it as
`CKTstate0[ccap] = ag[0]*q0 + ag[1]*q1 + ag[2]*q2`, with
`geq = ag[0]*cap` (`:78`).

espice hardcoded the **uniform-step** triple:

```zig
.gear_2 => 3.0 / (2.0 * dt),            // alpha == ag0
.half_inv_dt = if (use_gear) 1.0 / (2.0 * dt) else 0,   // == ag2
```

`(3/2, -2, 1/2)/dt` is BDF2 only while `dt == dt_prev`. Off a uniform grid it
is not second order and not even consistent as a derivative estimate of the
right thing. Every shipping gear deck is tmax-locked, so `dt` never varied and
the constants were never exercised. Tightening the LTE coefficient made `dt`
vary — `mos6_gear` went from `rej[lte=1] order_drops=0` to
`rej[lte=26] order_drops=13` — and the latent bug bit immediately.

**Fix.** At order 2 that Vandermonde solve has a closed form. With
`r = dt/dt_prev`:

```
ag0 = (1+2r)/((1+r)·dt)      ag1 = -(1+r)/dt      ag2 = r²/((1+r)·dt)
```

`r == 1` recovers the hardcoded triple exactly. `integrator.coeffs(method, dt,
dt_prev)` returns `{ag0, ag2}`; `ag1` is never materialised because
`ag0+ag1+ag2 = 0` (the corrector is exact on constants), so the existing
residual shape `ag0·(q − q1) − ag2·(q1 − q2)` is already the three-term sum.

Two consumers had the same hole and are fixed with it:

- `advanceCurrent` wrote `ag0·(q0 − q1)` for gear, i.e. the *backward-Euler*
  current, missing the `− ag2·(q1 − q2)` term. That array is `i_prev`, which
  is what `CKTterr`'s `volttol` reads.
- `stepBound`'s own `i_new` had a two-way `exec_trap` branch with no gear arm,
  so it recomputed the same BE current. It now takes `cur_method` (the method
  the step actually integrated with, which is what `CKTstate0[qcap+1]` holds
  when `CKTterr` reads it) separately from `method` (the one whose coefficient
  and order are being probed) — the BE→order-2 promotion probe needs those to
  differ, exactly as `dctran.c` does.

Pinned by `test "coeffs: BE 1/dt, trap 2/dt, gear-2 variable-step BDF2"`,
which checks `r == 1` against the old constants and then, for
`r ∈ {0.25, 0.5, 1, 2, 4}`, that the corrector is exact on the linear ramp and
on the quadratic through the actual node spacing.

BE and trapezoidal arithmetic is untouched (`ag2 == 0` is not multiplied in on
those arms — they are separate `switch` prongs, not a fused `− 0.0·x`), so
every non-gear deck stays bit-identical.

## The per-`ddt` LTE item — measured, and not worth doing

`todo.md` *Accuracy — documented architectural* → **per-`ddt` LTE states**, and
`docs/perf/fail-audit-2026-09-10.md` §2/§3, which attribute espice's only two
genuine accuracy losses (`ngspice/mosamp`, `devices/mos6_inverter`) to it. The
proposed fix is a VerA device-ABI event: emit one `D.q` per `ddt` contribution
instead of one per device unknown, so a MOSFET's `qgs`/`qgd`/`qgb` stop
arriving pre-summed on the gate row.

The framing to date has been "the finer bound is right, it costs 11x the
steps". Both halves of that are wrong, and the experiment that shows it is
cheap: build the **accuracy-vs-step-count frontier** for each granularity by
sweeping `trtol`, and see whether the finer index space moves the frontier or
merely slides along it.

`trtol` is the measurement knob here, not a proposed fix. Scaling it is
exactly what a granularity change does — both multiply the same `del` — so if
the two produce the same curve, they are the same knob.

### Why refining the index space costs steps at all

`CKTterr` is **homogeneous of degree zero in q**: `tol` scales with `|q|`
(both `volttol` and `chargetol`) and so does `|dd|`, so `del` depends only on a
state's *relative* curvature, never its size (pinned in
`test "stepBound: per-state min survives what the summed row cancels"`). A
split therefore does not merely "un-cancel" a divided difference — it adds
candidates to a `min`, each at full strength however small its charge. More
candidates, smaller `min`, more steps. That is arithmetic and it is
unconditional. Whether the extra candidates are *informative* is the open
question, and it is empirical.

### espice already contains both granularities

`ZP_NO_QTAPE=1` forces the per-row fallback on a live binary; the default is
per-device-state. That is a real index-space refinement of the same kind
per-`ddt` would be (per-row → per-(instance,terminal) → per-`ddt`). If
refinement placed steps better, the row→state step should already show it.

### What the frontiers say

**1. Refining the index space does not move espice's own frontier.** Per-row
and per-state trace the same accuracy-vs-steps curve on both decks — per-state
is marginally better at equal cost and no more. The one refinement espice can
actually perform, performed, changes where you sit on the curve and not the
curve. There is no reason to expect the next refinement to behave differently,
and `todo.md` already records that this same refinement made `mos6_inverter`
*worse* at its default `trtol` (1.7e-2 → 3.3e-2 max) and `kinduc` worse by four
orders — refinement is not monotone in accuracy.

**2. The "11x" is not a cost of correctness.** On mosamp espice's frontier
**dominates** ngspice's: at ngspice's own default accuracy (1.89e-3 rms,
2316 steps) espice needs ~250 steps — 9x cheaper. At 9.5e-4, 354 against 2330.
At 3e-4, 550 against ~2300. espice is 4-9x cheaper at equal accuracy across the
whole usable range. ngspice's 2316 steps buy nothing espice cannot buy for 550;
the `trtol` sweep shows why, since ngspice's count is nearly *flat* in `trtol`
(2316 → 3060 over 1000x) while its minimum `dt` collapses 400x (4.3e-12 →
9.5e-15). Those steps are discontinuity squeeze-throughs — the Meyer model's
region-boundary kinks, which per-`ddt` states expose and the summed gate row
smooths over — not resolution of smooth truncation error.

**3. Where ngspice is genuinely ahead, it is ahead by ~2x and then floors
out.** On mos6_inverter ngspice reaches 2.84e-4 rms in 480 steps where espice
needs ~1350, then stops improving (3.15e-4 at 622, 3.37e-4 at 898 — it gets
*worse*) while espice keeps descending to 1.72e-4. So even here the finer
granularity is a head start, not a better answer; espice reaches strictly lower
error than ngspice can, for ~2.5x the steps.

### Conclusion

Do not spend a device-ABI event on this. The cost framing in the fail audit
("11x slower if you simply switch granularity") is real as an observation about
ngspice's mosamp run and wrong as a claim about what the accuracy costs: on
that deck espice is already 4-9x more step-efficient than the engine whose
granularity was being held up as the target. The one deck where ngspice's
frontier is genuinely better, `mos6_inverter`, is a ~2.5x-steps trade over a
narrow band that ends in an ngspice error floor espice goes through.

The accuracy *cannot* be had cheaply, because it is not there to be had: the
finer bound is a step-count multiplier, arithmetically equivalent to lowering
`trtol`, which is the bandaid this work was told not to ship. Shipping it as a
device-ABI change would be the same bandaid with a much larger blast radius.

The two fixtures stay FAIL. They are a **1.3x / 1.8x accuracy trade against an
11x / 1.0x step-count advantage**, on a gate whose own reference
(`ngspice` default) is 1e-3…3e-3 rms from converged truth and FAILs that gate
itself. `todo.md`'s per-`ddt` item should be closed against this document
rather than left open as an architectural debt.

Left in place deliberately: the ~800-of-1800 hard `+0.0` rows in pi100's
`q_tape`. Checked, not assumed — a dead row has `dd == 0`, so its bound
collapses to `trtol·tol/abstol ≈ 7e4 s` and it can never be the `min`. It does
not interact with anything here.
