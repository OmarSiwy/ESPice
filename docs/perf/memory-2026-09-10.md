# Memory — full accounting and change ledger, 2026-09-10

espice's stated goal is to use much less memory than ngspice because it is
more data-oriented. It already won 221 of 225 decks; the losses were bad, and
the per-device constant was roughly 2x ngspice's. This is where the bytes
were, and what moved.

Reference deck: `benchmark/fixtures/sweep/opamp_wl_5000` — 5,000 electrically
independent 5T OTAs (25,000 MOS1 + 5,000 caps), n = 15,009, `.ac dec 10 1 1G`
(91 points). Peak RSS via `time -v`, same rig, same build flags.

## The instrument: `ZP_MEM_STATS=1`

Neither usual tool can see this program. massif hooks malloc and every large
allocation here goes through an arena over `smp_allocator`, which mmaps;
Release builds ship no symbols because `-Ddebug-info=true` SEGVs the Zig 0.16
compiler (`remaining-2026-09-10.md`). So the accounting lives in the code:
`src/mem_stats.zig`, on the same one-shot-`getenv` rule as `ZP_LU_STATS` /
`ZP_TRAN_STATS` / `ZP_OPDBG`. Off by default, and off means `track()` returns
the child allocator unchanged — no per-allocation cost at all.

Columns: `req` = bytes asked for under a label, cumulative, never decremented;
`live` = req minus what came back; `peak` = high-water of `live`; `n` = the
count the caller says the row scales with, so `req/n` travels between deck
sizes. On an arena `req` is the honest footprint — see the next section for
why. The report ends with the process's own `VmHWM`, so a table that does not
add up to peak RSS is missing a row rather than proving one.

Only allocators passed through `mem_stats.track()` are counted. Scratch that
is genuinely reclaimed (`smp_allocator`) reads as absent, by design: the table
answers "which table is the resident MB", and reclaimed scratch is not one.

## The root cause: `free` on an arena is a no-op

`ArenaAllocator.free` and shrink-`resize` return without reclaiming anything
that is not the arena's most recent allocation (std/heap/ArenaAllocator.zig
:564, :620). espice ran BOTH its circuit build and every analysis on arenas:

- `Builder.init(sim_arena)` — so `ProtoStore`'s three per-instance columns
  (`models`, `instances`, `nodes`) grew by `std.ArrayList`'s 1.5x rule on an
  allocator that could not take the abandoned capacity back. The three grow
  interleaved, one append each per device, so none of them is ever the arena's
  most recent allocation and not one realloc could be done in place. Sum of a
  1.5x geometric series: ~2x the final column size, dead, for the whole run.
- `RunCtx.allocator` is the results arena — so every `defer a.free(...)` in
  every analysis was a lie, and payload-sized intermediates stayed live
  alongside the result they were built into.

This is one cause with two sites, and it is what the missing ~3.8 KB per MOS1
instance was.

## Where the 143.9 MB of `.op` went (before)

`ZP_MEM_STATS=1 espice -b op5000.sp` (the reference deck with the `.ac` card
replaced by `.op`):

| label | req MB | live MB | B per n |
|---|---:|---:|---:|
| parse: source + AST | 19.79 | 19.05 | 691 / card |
| setup: engine + jobs | 5.53 | -8.52 | — |
| **mos1 staging** | **109.46** | **36.52** | — |
| circuit: pattern build | 9.38 | 9.38 | 15 / key |
| circuit: CSC + planes | 7.76 | 2.55 | — |
| capacitor staging | 1.29 | 0.43 | — |
| mos1 (frozen tapes) | 10.87 | 2.39 | 456 / inst |
| capacitor (frozen) | 0.23 | 0.10 | 48 / inst |
| run: solve + results | 13.46 | 7.21 | — |
| TOTAL req 177.79 | | | VmHWM **144.76** |

**`mos1 staging` is 109.5 MB for 36.5 MB of live columns.** 73 MB — half the
deck's entire `.op` footprint — was dead `ArrayList` capacity that nothing
could ever reclaim. Per instance that is 4.38 KB requested for 1.46 KB of
columns, i.e. **2.92 KB per instance of pure growth garbage**. That, plus the
parse AST at 691 B per card, is the ~3.8 KB the structural accounting could
not find.

Structurally accounted, per MOS1 instance (n_u = 8): `Model` 320 B (38 f64 +
i64 + 6 bools; note VerA puts W/L/AD/AS/PD/PS/NRD/NRS/M on the *Model*, so
one Model per instance is required, not a bug), `Instance` 856 B (106
f64-sized fields), `slots` 256 B, `gath`+`rhs_idx` 64 B, `lim_x` 64 B,
`q_tape` 64 B, `State` 8 B = **1,632 B**. That is exactly what the row reads
after the fix.

`saved_models` costs **zero**: no shipped device declares `attempt`
(`grep -l "pub fn attempt" .zig-cache/vera-check/*.zig` is empty), so
`has_attempt_decl` is false everywhere and the second copy is never allocated.
It is live contract surface (`VerA/tools/contract.zig:795`) for source
stepping, not dead weight today.

## Phase split (before)

| phase | MB |
|---|---:|
| `.op` only — setup + OP solve | 143.9 |
| AC solver workspace (2-point `.ac` minus `.op`) | 56.0 |
| results storage (91-point minus 2-point) | 60.7 |
| **total, 91-point `.ac`** | **260.6** |

The results row is NOT growth-by-doubling — `types.logSweepCount` sizes the AC
point count exactly and `ac.run` allocates exactly once. It is three live
copies of the same 21.9 MB payload, because all three came from the results
arena and none of the `defer`s could free: `resp` (probe-major, 21.9 MB),
`x_out` (the batch solution, 21.9 MB) and `data` (point-major, the Result,
21.9 MB). 3 x 21.4 = 64 MB, which is the row.

## Reproducing any of this

```sh
# the phase split: same deck, .ac card edited
sed 's/^\.ac dec 10 1 1G/.op/'        benchmark/fixtures/sweep/opamp_wl_5000/circuit.sp > op.sp
sed 's/^\.ac dec 10 1 1G/.ac dec 1 1 10/' benchmark/fixtures/sweep/opamp_wl_5000/circuit.sp > ac2.sp

time -v zig-out/bin/espice -b op.sp -r /tmp/o.raw       # "Maximum resident set size"
ZP_MEM_STATS=1 zig-out/bin/espice -b op.sp -r /tmp/o.raw   # the table

# speed: wall clock is unusable on a shared rig, use instruction counts
valgrind --tool=callgrind --callgrind-out-file=/dev/null \
  zig-out/bin/espice -b benchmark/fixtures/scaling/parallel_inverters_100/circuit.sp -r /tmp/o.raw
```

`.ac lin` is rejected (`UnsupportedFrequencySweep`), so the 2-point variant has
to be `dec 1 1 10`.

parse AST.

VmHWM 80.39 MB, and `mos1` reads 1,632 B per instance — the structural number
with no slack.

### 1+2. Build scratch off the arena (`ee6946a`)

Two sites, one cause, one commit.

#### ProtoStore staging

`engine.zig` gains `staging_gpa = std.heap.smp_allocator` and
`ProtoStore.append(model, instance, nodes)`; `finalize` replaces
`toOwnedSlice(gpa)` with `gpa.dupe(...)` plus an immediate
`deinit(staging_gpa)`. The frozen ABI is untouched — the batch still owns
exact `[]D.Model` / `[]D.Instance` slices from `gpa`, and `hooks.deinit` still
frees them there.

Why a real allocator rather than an exact reserve: the per-type instance count
is not knowable without duplicating the level dispatch, and reserving a letter
bucket's size per type is worse than the status quo once a bucket holds four
or more device types. `smp_allocator` routes everything >= 64 KB straight to
`PageAllocator.map`/`unmap`, so an abandoned column is `munmap`ed and its
growth realloc is an `mremap` — no heuristic, correct at every deck size.

Peak carries one type's columns twice during its `finalize`, never every
type's dead capacity forever: 109.5 MB resident -> 38.9 MB, on the reference
deck.

#### PatternBuilder + radix scratch

`pb.keys` holds one `u64` per stamp site *before* dedup — 650,017 keys on this
deck for 115,017 nonzeros — and `radixSort` allocates a same-sized ping-pong
buffer plus a 256 KB histogram. All three die inside `Circuit.init`; all three
were resident for the whole run. `Circuit.init` now passes `smp_allocator` for
them and `toCsc` takes `gpa` and `scratch` separately. No vtable change: the
allocator `Proto.pattern` receives was only ever used for the PatternBuilder.

14.6 MB -> 0 resident (`circuit: pattern build` leaves the table; `circuit:
CSC + planes` drops 7.76 -> 2.55 MB, now all live).

### 3. Analysis scratch onto `RunCtx.scratch_allocator` (`e7ee882`)

`RunCtx.scratch_allocator` already existed — "reclaimable work storage when
allocator retains the final results in an arena" — and exactly one analysis
used it (`tran.zig:793`). Every other leaf allocated its scratch from
`ctx.allocator`, which is the results arena.

The rule applied, mechanically and provably: **a buffer `defer`-freed in the
same scope is scratch and must come from the scratch allocator; a buffer only
`errdefer`-freed is the Result and stays on `ctx.allocator`.** 18 files:
`ac/{ac,noise,sp,stb}`, `dc/{dc,dcmatch,tf}`, `post/{four,disto}`,
`eigen/pz`, `pss/{pss,pac,pnoise,pxf,hb,qpss}`, `sweep/{mc,sens,temp_sweep}`,
`tran/{envelope,matex,tran_noise}`.

On the reference deck's `.ac` that is `resp` + the FreqSolver workspace +
`x_out` reclaimed at the end of the sweep, leaving `data` alone: results
storage 60.7 -> 20.8 MB against a 21.9 MB payload, i.e. the 2.9x overshoot is
now 1.0x.

## Cost: small decks pay ~0.6-0.9 MB

`scaling/parallel_inverters_100` 5.5 -> 6.1 MB, `devices/mos6_inverter`
5.0 -> 5.9 MB. `smp_allocator` maps a fresh 64 KB slab per size class per
thread, so a deck whose staging columns are all under 64 KB now pays slab
granularity where it used to share an arena chunk. Both decks remain about
half of ngspice's ~11.8 MB floor, and the trade buys 46.8% on the deck that
was losing. Not worth a size heuristic.

rig runs at load 25):

|---|---:|---:|
| `scaling/parallel_inverters_100` | 466,362,794 | 466,350,100 |

Both within 0.003%. Both figures are on 446268a; `remaining-2026-09-10.md`'s

`ZP_MEM_STATS` adds no instructions to any per-device or per-timestep loop:
the only `enter`/`leave` pairs are per deck phase and per device *batch*, and
each is one cached-bool branch when the variable is unset.

## Priced and NOT done

### Dedupe `Model` by value into a table + `model_of: []u32`

The frozen-ABI rule permits it (host tables are ours), but the arithmetic does
not. VerA puts W/L/AD/AS/PD/PS/NRD/NRS/M on `Model`, so a per-instance `Model`
is semantically required, and dedup can only be by value. On this deck 5,003
of 25,000 Models are distinct (M1/M2 sweep W and L; M3/M4/M5 are fixed), so
value-dedup saves 20,000 x 320 B = **6.4 MB of 138.7**, minus 100 KB for the
index. On `parallel_inverters_2000` it is 2 distinct of 4,000, saving 1.3 MB.

The cost is an extra dependent load (`&models[model_of[i]]`) in the innermost
device-eval loop, on every instance of every Newton iteration of every
timestep. We win 209 of 225 decks on speed and 4.6% of memory is not worth
risking that. Declined.

### Move the 62 `pc__` slots and the simulation-global fields off `Instance`

`remaining-2026-09-10.md` §10 already names this. Measured value: 62 f64 =
496 B per instance, 25,000 instances = **12.4 MB of 138.7 (8.9%)**. The
simulation-global fields (`temperature`, `abstime`, `dt`, `mfactor`,
`analysis_kind`, three step-phase bools, `is_analog_initial`, `systf`,
`bound_step`, `discontinuity_order`) are another ~64 B per instance = 1.6 MB
(1.2%); their real cost is write bandwidth, not memory.

This IS a `Model`/`Instance` POD layout change, so it needs VerA codegen, a
`layoutHash` bump and coordinated GPU-side changes — and the prefix-latch that
put those slots on the Instance bought -3.68% on `bsim4_transfer`. 10% of
memory for an ABI break and a speed risk, against changes 1-3 that took 47%
for neither. **Sequence it separately; it is not this commit's fight.**

### Widen the streaming gate past `.tran`

`main.zig:268` gates streaming on `format == .binary and n_jobs == 1 and
activeTag(jobs[0]) == .tran`, so only the transient streams. `rawfile.Stream`
already reserves the header and patches `No. Points:` in `finish()`, but
`writeHeader`'s `is_complex` path is written for the retained-array case: the
`Variables:` block and the `Binary:` payload both assume the whole plot is in
hand, and the AC row order is (re, im) interleaved per variable rather than
the transient's (time, probes...). Extending it is a real change to
`output/rawfile.zig` plus a per-point `Result` shape the analyses do not have.

Not needed now: exact pre-sizing was never the AC problem (`logSweepCount` is
exact), and change 3 already took results storage to 1.0x of payload.
Streaming would take it to ~0, i.e. another 20.8 MB of 138.7, at the price of
a new whole-deck streaming contract. Revisit when a single analysis's payload
is again the dominant row.

### Overlap of the parse AST with the built device tables

`main.zig:260` resets the parse arena only after `fromNetlist` returns, so the
AST and the device tables are live together. Quantified: **19.79 MB on a
35,016-line netlist (691 B per card)**, 24.6% of the post-fix `.op` peak — and
**0% of the deck's actual peak**, because the arena is reset before the AC
phase, which is where peak RSS is. It costs peak only on `.op`-only and
`.dc`-only decks. Removing it means a streaming parse (build devices card by
card), which is a frontend rewrite. Recorded, not done.
