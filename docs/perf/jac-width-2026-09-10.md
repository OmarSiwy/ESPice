# The Jacobian width belongs to the instantiation, not the device

2026-09-10, branches ARPice `jac-width` / VerA `jac-width-vera`.
Scope: `docs/perf/gpu-layout-2026-09-10.md` §8 (`jac_f32` is 1.21× on the GPU
and the prerequisite for beating ngspice at all) against
`docs/perf/jac-f32-2026-09-10.md` (`jac_f32` costs `ngspice/mosmem` +13.7% on
the CPU). Both are true. Until now they had to be answered with one number.

**Result: one binary runs an f32 Jacobian in the GPU kernel and an f64
Jacobian on the CPU. 257 of 257 fixture raws byte-identical to the previous
build, 287 of 287 exit codes identical. GPU `parallel_inverters_2000`
927 → 799 ms (1.16×, 7 interleaved rounds), `arp_eval_mos1` 2289 → 1243
f64-pipe ops and 254 → 176 registers, NR 1356 → 1354, and
`scaling/inverter_chain_4k` now PASSes on `--backend cuda` where it timed out
before. `zig build test` 413/413.**

---

## 1. Where the width comes from now

Three things that used to be one:

| | decl | who emits it | who reads it |
|---|---|---|---|
| **permission** — the physics survives 7 digits | `pub const jac_f32` | VerA `--jac-f32`, ESPice `-Djac-f32-gpu=<stems>` | `engine.gpuJacFloat` |
| **host order** — the CPU should take it anyway | `pub const jac_f32_host` | VerA `--jac-f32-host`, ESPice `-Djac-f32=<stems>` | `engine.jacFloat` |
| **taking it** | — | — | one comptime argument to `evalRange` |

```zig
pub fn jacFloat(comptime D: type) type {      // host
    return if (@hasDecl(D, "jac_f32_host") and D.jac_f32_host) f32 else f64;
}
pub fn gpuJacFloat(comptime D: type) type {   // device kernel
    return if (@hasDecl(D, "jac_f32") and D.jac_f32) f32 else f64;
}
```

`jac_f32_host` implies `jac_f32` — codegen emits both and `tools/contract.zig`
rejects the pair with the permission missing, because a host width without a
permission is the one combination that means nothing.

A device the physics keeps at f64 declares neither and is f64 on **both**
paths, which is the property `engine.zig`'s original comment asked for and
the reason the permission stays on the device.

## 2. How the two instantiations diverge

Exactly the way `rank4-collapse` split the derivative *basis*
(`docs/perf/rank4-2026-09-10.md` §3). `evalRange` gains one more comptime
parameter and nothing else moves:

```zig
fn evalRange(comptime D: type, comptime narrow: bool, comptime F: type,
             sink: anytype, first: u32, end: u32, t: f64, limiting: bool) void
    ...
    const S = DualFor(W, F, @hasDecl(D, "collapse"));
```

Three call sites, one body:

| caller | `narrow` | `F` |
|---|---|---|
| `DeviceBatch.evalInner`, collapsed instances | `true` | `jacFloat(D)` |
| `DeviceBatch.evalInner`, the rest | `false` | `jacFloat(D)` |
| `DeviceKernel.run` (the GPU entry) | `false` | `gpuJacFloat(D)` |

That is the whole diff in the kernel. Same body, same `D.evalQ` call, same
`DualFor` constructor, same `Sink`, one comptime width apart — which is
AGENTS.md's scalar-oracle rule and not a breach of "No GPU-only kernel logic".
**A width parameter is not logic.** There is still one physics body; it is
instantiated at two widths, exactly as `narrow` already instantiates it at two
basis ranks. If the two ever need different *code*, that is the thing to
refuse, and this change does not do it.

### Nothing at the frozen boundary moved

Checked, not assumed. `F` is a comptime type inside `Dual`, so:

- **`DeviceKernel.run`'s parameter list is unchanged** — same 13 arguments,
  same types. No kernel-argument change, which is what the freeze is about.
- **The residual is f64 on both instantiations.** `Dual.v` is `f64`
  unconditionally and every boundary of the contract's S protocol
  (`con`/`scale`/`addC`/`val`/`ddxAt`) is f64, so the device never sees `F`.
  `engine.test."Dual: an f32 Jacobian leaves the residual bit-identical"`
  pins this directly, and it is why the answer is fixed by the residual.
- **The planes stay `[]f64`.** `grad()`/`ddxAt` widen back before the
  `atom.global.add.f64` scatter; `g_vals`/`c_vals`/`rhs`/`q_vec` are
  untouched.
- **Scatter tapes (`gath`/`rhs_idx`/`slots`, u32), Model/Instance PODs,
  pattern CSC: untouched.** They are keyed on types that do not contain `F`.
- **`layoutHash` does not move**, and did not have to: `DeviceVtable`, `Proto`,
  `Batch`, `Hooks`, `Planes`, `PatternView`, `PatternBuilder`, `ParamRef`,
  `NoiseSource` are all unchanged, and `abi_version` stays 7. A `.so` device
  built before this change is still ABI-compatible, and it picks its own two
  widths from its own two decls through the same `engine.zig`.

`collectNoise` — the one host consumer of a `Dual` outside `evalRange` — takes
`jacFloat(D)`, i.e. the host width. It runs on the host.

## 3. What `-Djac-f32` means now

| flag | default | effect |
|---|---|---|
| `-Djac-f32-gpu=<stems>` | **`mos1,mos6`** | those models' GPU kernels carry an f32 Jacobian; their CPU kernels do not |
| `-Djac-f32=<stems>` | *(empty)* | those models are f32 **on the CPU too** — and, since the host order implies the permission, on the GPU |

`-Djac-f32=<stems>` therefore still means exactly what it meant when
`docs/perf/jac-f32-2026-09-10.md` was measured: a build where the listed stems
run f32 everywhere. **Verified, not assumed** — see §5.3. The CPU experiments
in that document reproduce from the same command line they were taken with.

The **default permission list is `mos1,mos6`**, and it is the measured set, not
a guess:

- `mos1` — GPU 1.21× on record and 1.16× re-measured here, agreement and
  iteration counts below.
- `mos6` — same `n_u = 8`, same `U = {d,g,s,b,di,si,flow,flow}`, same accuracy
  sweep (57 decks, `jac-f32-2026-09-10.md`). Its kernel narrows by the same
  construction, measured: `arp_eval_mos6` 2846 → 1448 f64-pipe ops, 254 → 168
  registers. No GPU deck in the corpus instantiates mos6 today, so this is the
  one entry with no end-to-end GPU timing; it is in because the *physics*
  question — do the unknowns fit in 7 digits — was answered for it, and that
  is the question the permission asks.
- `diode` and `bsim4va` are **out by measurement**, not caution: the diode
  kernel is 4–5% slower under f32 on the CPU, bsim4va is 0.0%, and
  `gpu-device-eval.md` §9.5 measured mos9 and diode on the GPU at 0.0%.
  `gompute_diode.ptx` is byte-for-byte the same 983 f64 ops in both builds —
  the control that proves the default list is a list and not a global switch.

## 4. Measured

Baseline is a clean worktree of this tree's branch point (`99e41b6`), built
from the same `../VerA` (the VerA change is additive and emits nothing without
a flag — pinned by `codegen: --jac-f32 adds a permission decl and changes not
one other byte`). Both trees `zig build` at the default `ReleaseFast`, GPU
kernels on.

### 4.1 The GPU kernel

`arp_eval_mos1`, static mnemonic counts over the `.visible .entry` body of
`.zig-cache/o/*/gompute_mos1.ptx`, registers and occupancy from the driver
through `libcuda.so.1` (no `ncu`/`cuobjdump` on this machine —
`gpu-layout-2026-09-10.md` §10):

| | f64 jac (base) | **f32 jac (new)** | on record (§8.2) |
|---|---:|---:|---|
| f64-pipe ops | 2 289 | **1 243** | 2 028 → 1 074 |
| f32-pipe ops | 0 | 1 143 | 0 → 952 |
| …of which `cvt` f32↔f64 | 0 | **187** | 187 |
| 64-bit vregs | 3 698 | 2 640 | 3 911 → 2 853 |
| physical registers | 254 | **176** | 248 → 183 |
| local (spill) | 0 B | 0 B | 0 B |
| blocks/SM @ 256 | 1 | 1 | unchanged |

(The absolute counts differ slightly from §8.2 — that measurement predates
`limit-body` and `rank4-collapse` — but every ratio and the `cvt` count
reproduce.)

`arp_lim_mos1` is **974 f64 ops and 96 registers in both builds**, to the
digit. The limit/state pass works on the clamp and the residual, not the
derivative vector, so there is nothing in it to narrow. Same result as §8.2.

`arp_eval_mos6`: 2 846 → 1 448 f64 ops, 254 → 168 registers, spill 40 → 32 B.
`arp_eval_diode` (no permission): 983 → 983, unchanged.

### 4.2 Wall clock, interleaved

`scaling/parallel_inverters_2000`, whole process (`-b`, raw written), the two
binaries and the two backends interleaved round by round, 7 rounds, load ~9
(other agents building):

| arm | median | min | max |
|---|---:|---:|---:|
| base `--gpu` (f64 jac) | 927 ms | 880 | 1026 |
| **new `--gpu` (f32 jac)** | **799 ms** | 766 | 823 |
| | **1.16×** | | |
| base `--backend cpu` | 754 ms | 727 | 771 |
| new `--backend cpu` | 776 ms | 736 | 823 |
| | 1.03× — noise, see below | | |

**1.16× on the GPU**, against 1.207× on record. The gap is machine state: that
measurement was taken at load ~19 on a tree without `limit-body`/`rank4`, and
this one shares the box with three other build jobs. The CPU column moves 3%
in the *other* direction and that is pure measurement noise — the two CPU
binaries produce **byte-identical output on every deck in the corpus** (§5.1),
so there is no numerical difference for a time difference to come from.

### 4.3 Iteration counts — `ZP_TRAN_STATS`, same deck

| arm | accepted | attempts | `nr_iters` | rejections |
|---|---:|---:|---:|---|
| base cpu | 595 | 613 | 1356 | `newton=0 lte=18 state=0` |
| base gpu | 595 | 613 | 1356 | same |
| **new cpu** | 595 | 613 | **1356** | same |
| **new gpu** | 595 | 613 | **1354** | same |

The CPU is unchanged, and the GPU reproduces §8.2's **1356 → 1354** exactly:
the inexact-Newton tax on this deck is negative. `order_drops=9`,
`bp_landings=20`, `avg_dt=8.403e-11` on all four arms — the timestep grid does
not move, which matters for reading §4.4.

### 4.4 GPU/CPU agreement

`parallel_inverters_2000`, all 1 194 980 samples of the transient, deviation
normalised by the bench runner's own rule (`max(peak, span, 1)` per variable):

| pair | max | RMS |
|---|---:|---:|
| base CPU f64 vs base GPU f64 | 2.3e-14 | 6.2e-17 |
| **new CPU f64 vs new GPU f32** | **8.4e-7** | **2.5e-8** |
| base GPU f64 vs new GPU f32 | 8.4e-7 | 2.5e-8 |
| base CPU vs new CPU | **0** | **0** |

Read the rows together. The GPU path itself is exact to 2.3e-14 against the
CPU; the entire 8.4e-7 is the f32 Jacobian, and it is identical whether you
compare the new GPU against this build's CPU or against the old build's GPU.
Since the accepted timestep grid is the same on all four arms (§4.3), this is
not a moved grid — it is the width of the tolerance band an inexact Jacobian
converges inside.

On the recorded **3.9e-10**: that figure is one flagged sample
(−0.003149681814093183 vs −0.003149681815312781), not a corpus maximum, and it
is not the same statistic as the table above. The comparable published number
is `jac-f32-2026-09-10.md`'s f32-vs-f64 sweep, where `parallel_inverters_100`
came in at **3.11e-7 max relative / 1.85e-8 RMS** — the same order as the
8.4e-7 / 2.5e-8 measured here on a deck 20× the size. Against the suite's own
pass rule (RMS ≤ 1e-3, max ≤ 1e-2) there are four orders of margin.

### 4.5 GPU fixture verdicts

`check_fixtures.py --backend cuda`:

| category | base | new |
|---|---|---|
| `scaling` | 13/14 | **14/14** |
| `devices` | 85/111 | 85/111 |

The one that moved is **`scaling/inverter_chain_4k`**, which timed out at 60 s
on the base build and PASSes on the new one. This is
`gpu-layout-2026-09-10.md` §8.3 landing by default: with an f32 Jacobian the
4 000-stage chain's operating point converges directly instead of burning
93 070 iterations in the pseudo-transient fallback. §8.3 is explicit that this
is **luck, not a fix** — the deck sits on the knife edge of the op continuation
ladder (`converger.zig:581`), and `ESPICE_SOLVER=jfnk` rescues it just as well.
It is recorded here because it is now the shipped behaviour on the GPU, and
because the same deck still fails on the **CPU** (f64 there), which is the
clearest possible demonstration that the two instantiations are genuinely
different.

## 5. The checks

### 5.1 CPU bit-identity — the whole corpus, `cmp`, not assumption

```
./benchmark/capture_raws.sh /tmp/raws-before   # espice-base @ 99e41b6
./benchmark/capture_raws.sh /tmp/raws-after    # this tree
```

- **257 of 257 `.raw` files byte-identical** (`cmp -s`, zero diffs).
- **287 of 287 exit codes identical** (`diff exits.txt`).

This is the load-bearing check and it is stronger than "the fixtures pass":
`mos1` and `mos6` *do* carry the permission in this build, and the CPU
declining it is the only reason `devices/mos6_inverter`,
`scaling/parallel_inverters_*`, `ngspice/mosmem` and the 253 others come back
bit-for-bit. Had `jacFloat` read the permission instead of the order, 35 of
these would have moved (the 57-deck sweep in `jac-f32-2026-09-10.md` found 22
bit-identical and 35 not).

### 5.2 The host really declined it — proved by the deck built to tell

`convergence/mos_latch_ladder` exists precisely because it discriminates an
f32 Jacobian from an f64 one on the CPU (`docs/perf/ladder-deck-2026-09-10.md`):
three cold OP solves over the write sweep, and under f32 two of them lose plain
Newton and pay the gmin ladder.

```
ZP_OPDBG=1 espice -b --backend cpu -r /dev/null \
  benchmark/fixtures/convergence/mos_latch_ladder/circuit.sp
```

| build | `ladder: plain` | `plain conv=true` | `ladder: gmin` |
|---|---:|---:|---:|
| base (`99e41b6`) | 3 | **3** | 0 |
| **this tree, default** | 3 | **3** | 0 |
| this tree, `-Djac-f32=mos1,mos6` | 3 | **1** | **22** |

Row 2 is the result: the host took f64 even though `mos1` carries the
permission. Row 3 is §5.3.

### 5.3 `-Djac-f32` still does what it always did

`zig build -Dgpu=false -Djac-f32=mos1,mos6 -p /tmp/jacf32-host-out` produces a
generated `mos1.zig` carrying **both** `jac_f32` and `jac_f32_host`, and the
ladder deck reads **3 / 1 / 22** — the exact signature
`ladder-deck-2026-09-10.md` recorded for `-Djac-f32=mos1`. The CPU experiments
in `jac-f32-2026-09-10.md` reproduce from their original command line.

### 5.4 Suites

- `zig build test --summary all`: **339/339 steps, 413/413 tests**.
- VerA `zig build test`: **279/280**, the same one pre-existing failure
  (`codegen: §5.6.5 a zero-short switch branch emits a collapse hook`) that
  fails on VerA `020c159` in a clean worktree. Not this change.
- `check_fixtures.py --category scaling` 13/14 and `--category convergence`
  5/5 on the CPU, unchanged.

### 5.5 The check left behind

`engine.test."jac width: one device, two instantiations"` — three stub device
types (no decl / permission only / permission + order) against `jacFloat` and
`gpuJacFloat`. Six assertions. If the two predicates are ever collapsed back
into one, the GPU loses its 1.16× or the CPU inherits `mosmem`'s gmin ladder,
and this is the cheapest place for that to surface.

`codegen: --jac-f32 adds a permission decl…` is extended with the one
invariant the split needs from VerA: `--jac-f32-host` emits the permission
too, so the combination `contract.zig` refuses can never be generated.

## 6. The CPU question, now that a deck can answer it

The brief asks what the evidence supports for mos1/mos6 **on the CPU**, given
that `convergence/mos_latch_ladder` is in the corpus for the first time.

**The evidence supports leaving the CPU at f64, and it is no longer "f64
because latches".** It is f64 because the only two decks in the corpus that
exercise a MOS operating point near a metastable write point both lose plain
Newton under f32, and they are the two that carry the whole cost:

| deck | f64 | f32 | cost |
|---|---|---|---|
| `ngspice/mosmem` | `plain conv=true`, OP 50 iterates | `plain conv=false`, OP 144 | +13.7% whole run |
| `convergence/mos_latch_ladder` | 3/3 plain, 0 gmin rungs, 360 iterates | 1/3 plain, 22 gmin rungs, 547 | +52% Newton work |

against −6.4% on `parallel_inverters_100` and −5.1% on `mos6_inverter`. Two
decks pay 14–52% so that two decks can save 5–6%. On this corpus that is not a
trade worth taking, and the corpus is now the *right* corpus — `mos_latch_ladder`
was built for this question.

**What a measurement would have to show to flip it.** The cost is not
distributed, it is concentrated on operating points where plain Newton is
marginal, so the question is a frequency, not a magnitude:

1. A stiff-MOS population, not two decks. `mosmem` was found by accident and
   `mos_latch_ladder` was reduced from it; 2/2 of the discriminating decks
   in the tree descend from **one** circuit. Ten independent MOS decks whose
   OPs sit near a basin boundary, with fewer than ~2 of them losing rung 1,
   would say the +13.7% is a tail and not the mode.
2. The gate-deck win holding at full corpus scale — the −6.4% is measured on
   two `parallel_inverters` decks and one `mos6_inverter`, all of which are
   arrays of the same inverter.
3. Net whole-suite wall clock over all 287 decks, f32 host vs f64 host, since
   that is the number the trade is actually about. It was never taken.

Cheaper than any of that, and now unblocked by this change: the width is a
**call-site argument**, so `DeviceBatch.evalInner` could take f32 for the
transient and f64 for the operating-point solve — which is exactly where the
whole cost lives (`mosmem` loses 94 OP iterates and gains 7 transient ones).
`jac-f32-2026-09-10.md`'s closing line called that "a real change, not a flag"
because the width was baked into the type. It is now one `if` in one function.
**Not done here** — it needs its own measurement pass, and nothing in the brief
asked for a CPU default change. `ponytail:` noted, not built.

## 7. What was NOT done

- **No per-instantiation width for `evalQRange`/`limitRange`.** Neither
  carries a derivative; `RealFor` is the value half and has no `F`.
- **No f32 anywhere but the derivative vector.** Not the residual, not the
  planes, not the LU. `direct.Solver` is `SolverT(f64)` and
  `iter_refine_steps` is still 0 — see `jac-f32-2026-09-10.md` §"Iterative
  refinement" for why refinement could not help an inexact *Jacobian* anyway.
- **No GPU narrowing** (`narrow = false` in `DeviceKernel.run`, unchanged) and
  **no `n_u > 8` narrowing**. Those are `rank4-2026-09-10.md` §5's items and
  are orthogonal: `canNarrow` reads the basis, never the float width, so the
  two comptime parameters do not interact. A device can be narrow-and-f64 (the
  CPU's mos1), wide-and-f32 (the GPU's mos1), or either alone.
- **No automatic permission.** VerA does not infer `jac_f32` from the model's
  unknown ranges. That would be the honest home for it and it is a real
  analysis; the build-time list is the shim, and it is where the policy already
  lived.

## Settled by this pass

| claim | the measurement |
|---|---|
| one binary can run two widths of the same kernel | `arp_eval_mos1` 1243 f64 ops on the device and 2289 on the host, same build, same `evalRange` |
| the CPU is untouched by it | 257/257 raws byte-identical, 287/287 exits, `mos_latch_ladder` 3/3 plain on both |
| the GPU keeps the win | 927 → 799 ms (1.16×), 254 → 176 registers, NR 1356 → 1354 |
| the answer survives | max 8.4e-7 / RMS 2.5e-8 over 1.19M samples against four orders of pass-rule margin, on an unmoved timestep grid |
| nothing at the frozen boundary had to move | `DeviceKernel.run`'s 13 arguments, `layoutHash`, `abi_version = 7`, the u32 tapes and the `[]f64` planes all unchanged |
| `-Djac-f32` still reproduces the CPU study | `3 / 1 / 22` on the ladder deck, the recorded f32 signature |

## Reproducing

```
git worktree add ../espice-base 99e41b6 --detach && (cd ../espice-base && zig build)
zig build

./benchmark/capture_raws.sh /tmp/raws-before   # from ../espice-base
./benchmark/capture_raws.sh /tmp/raws-after    # from here
diff /tmp/raws-before/exits.txt /tmp/raws-after/exits.txt
for f in /tmp/raws-before/*.raw; do cmp -s "$f" "/tmp/raws-after/$(basename $f)" || echo "DIFF $f"; done

D=benchmark/fixtures/scaling/parallel_inverters_2000/circuit.sp
ZP_TRAN_STATS=1 zig-out/bin/espice -b --gpu         -r /tmp/n_gpu.raw $D
ZP_TRAN_STATS=1 zig-out/bin/espice -b --backend cpu -r /tmp/n_cpu.raw $D

ZP_OPDBG=1 zig-out/bin/espice -b --backend cpu -r /dev/null \
  benchmark/fixtures/convergence/mos_latch_ladder/circuit.sp | grep ladder:

python3 benchmark/check_fixtures.py --category scaling --backend cuda
```

PTX op counts are static mnemonic counts over the `.visible .entry` body in
`.zig-cache/o/*/gompute_<model>.ptx`; registers/spill/occupancy come from
`libcuda.so.1` (`cuModuleLoadData` + `cuFuncGetAttribute` +

`/run/opengl-driver/lib/libcuda.so.1`, driver 595.71.05, RTX 4060 Laptop.
