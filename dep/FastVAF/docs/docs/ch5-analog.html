Chapter 5 — Analog Behavior

The description of analog behavior consists of setting up contributions for various signals under procedural or timing control.

5.2 Analog Procedural Block

Continuous-time behavioral description is encapsulated within the analog procedural block. The analog block defines behavior as a procedural sequence of statements. Conditional and looping constructs are available. Because this is a continuous-time description, no blocking event control statements (blocking delays, blocking events, or waits) are supported.

All statements within the analog block are executed sequentially at a given point of time; however, the effects on analog variables, nets, and branches are considered concurrently. Analog blocks shall be executed at every point in a simulation. Multiple analog blocks can be used within a module declaration.

analog_construct ::=
    analog analog_statement
  | analog initial analog_function_statement

analog_statement ::=
    { attribute_instance } analog_loop_generate_statement
  | { attribute_instance } analog_loop_statement
  | { attribute_instance } analog_case_statement
  | { attribute_instance } analog_conditional_statement
  | { attribute_instance } analog_procedural_assignment
  | { attribute_instance } analog_seq_block
  | { attribute_instance } analog_system_task_enable
  | { attribute_instance } contribution_statement
  | { attribute_instance } indirect_contribution_statement
  | { attribute_instance } analog_event_control_statement

analog_statement_or_null ::=
    analog_statement
  | { attribute_instance } ;

5.2.1 Analog Initial Block

The analog initial block is a special analog block, beginning with the keywords analog initial, for simulation initialization purposes.

Like a regular analog block, an analog initial block is comprised of a procedural sequence of statements. If there are multiple analog initial blocks, they are executed as if concatenated.

Statements in analog initial blocks shall not contain:

  • Statements with access functions or analog operators
  • Contribution statements
  • Event control statements

An analog initial block is executed before a matrix solution is available. Digital values cannot be accessed from the analog initial block as they have not yet been assigned.

The analog initial block is executed once for each analysis, and can be executed for each sub-task of parameter sweep analysis (such as dc sweep). If a parameter or variable referenced from an analog initial block is changed during a sub-task of a parameter sweep analysis, the analog initial block shall be re-executed so that the new value is taken into account.

5.3 Block Statements

Block statements (sequential blocks) group procedural statements. Statements within the block are executed in sequence, one after another in the given order. Control passes out of the block after the last statement. Block statements are delimited by begin and end.

5.3.1 Sequential Blocks

analog_seq_block ::=
    begin [ : analog_block_identifier { analog_block_item_declaration } ]
    { analog_statement } end

analog_block_item_declaration ::=
    { attribute_instance } parameter_declaration ;
  | { attribute_instance } integer_declaration
  | { attribute_instance } real_declaration

5.3.2 Block Names

A sequential block can be named by adding : block_identifier after the keyword begin. Naming a block allows local variables to be declared for that block and provides a means of uniquely identifying all variables at any simulation time.

All named block variables are static -- a unique location exists for all variables and leaving or entering the block does not affect the values stored in them. All identifiers declared within a named sequential block can be accessed outside the scope in which they are declared. Named block variables cannot be assigned outside the scope of the block in which they are declared.

Parameters declared within a named block have local scope and cannot be assigned outside the scope. Named and ordered parameter overrides at module instantiation can only affect parameters declared at module scope.

module example;
    parameter integer p1 = 1;
    real moduleVar;
    analog begin
        begin: myscope
            parameter real p2 = p1;
            real localVar = 1.5 * p2;
        end
        moduleVar = myscope.localVar;   // allowed
    end
endmodule

module top;
    example #(.p1(4)) inst1();          // allowed
    example #(.myscope.p2(4)) inst2();  // error
endmodule

5.4 Analog Signals

Analog signals are distinguished from digital signals in that an analog signal has a discipline with a continuous domain.

5.4.1 Access Functions

Flows and potentials on nets, ports, and branches are accessed using access functions. The name of the access function is taken from the discipline of the net, port, or branch associated with the signal.

For a named electrical branch b where electrical has V as the potential access function and I as the flow access function: the potential (voltage) is accessed via V(b) and the flow (current) via I(b).

  • There can be any number of named branches between any two signals.
  • Unnamed branches are accessed by applying access functions to net or port names rather than branch names.
  • If n1 and n2 are electrical nets or ports, then V(n1, n2) creates an unnamed branch from n1 to n2 (if it does not already exist) and accesses the branch potential. V(n1) does the same from n1 to the global reference node (ground).
  • There can only be one unnamed branch between any two nets, or between a net and implicit ground (in addition to any number of named branches).
  • An analogous access method is used for flows: I(n1, n2) creates an unnamed branch and accesses the branch flow.
  • The flow through a port into a module is accessed using <> delimiters: I(<p1>) accesses the current flow into the module through port p1.

5.4.2 Probes and Sources

5.4.2.1 Probes

If no value is specified for either the potential or the flow, the branch is a probe. If the flow of the branch appears in an expression anywhere in the module, the branch is a flow probe; otherwise it is a potential probe. Using both the potential and the flow of a probe branch is illegal.

  • The branch potential of a flow probe is zero (0).
  • The branch flow of a potential probe is zero (0).

5.4.2.2 Sources

A branch (named or unnamed) is a source branch if either the potential or the flow of that branch is assigned a value by a contribution statement anywhere in the module. It is a potential source if the branch potential is specified and a flow source if the branch flow is specified.

A branch cannot simultaneously be both a potential and a flow source, although it can switch between them (a switch branch).

Both the potential and the flow of a source branch are accessible in expressions anywhere in the module.

5.4.3 Accessing Flow Through a Port

The port access function accesses the flow into a port of a module. The access function name is derived from the flow nature of the discipline of the port. The port name is delimited with <> instead of ().

module diode (a, c);
    inout a, c;
    electrical a, c;
    branch (a, c) i_diode, junc_cap;
    parameter real is = 1e-14, tf = 0, cjo = 0, imax = 1, phi = 0.7;
    analog begin
        I(i_diode) <+ is*(limexp(V(i_diode)/$vt) - 1);
        I(junc_cap) <+
            ddt(tf*I(i_diode) - 2*cjo*sqrt(phi*(phi*V(junc_cap))));
        if (I(<a>) > imax)
            $strobe( "Warning: diode is melting!" );
    end
endmodule

The expression V(<a>) is invalid for ports and nets where V is a potential access function. The port access function shall not be used on the left side of a contribution operator <+.

An ideal relay (controlled switch):

module relay (p, n, ps, ns);
    inout p, n, ps, ns;
    electrical p, n, ps, ns;
    parameter vth=0.5;
    integer closed;
    analog begin
        closed = (V(ps,ns) > vth ? 1 : 0);
        if (closed)
            V(p,n) <+ 0;
        else
            I(p,n) <+ 0;
    end
endmodule

A discontinuity of order zero (0) is assumed to occur when the branch switches; it is not necessary to use $discontinuity with switch branches.

5.4.4 Unassigned Sources

If a value is not assigned to a branch, and it is not a probe branch, the branch flow is set to zero (0).

if (closed)
    V(p,n) <+ 0;

is equivalent to:

if (closed)
    V(p,n) <+ 0;
else
    I(p,n) <+ 0;

5.5 Accessing Net and Branch Signals and Attributes

5.5.1 Accessing Net and Branch Signals

Signals on nets and branches can be accessed only by the access functions of the discipline associated with them or by the generic potential or flow access functions.

nature_access_function ::=
    nature_attribute_identifier
  | potential
  | flow

branch_probe_function_call ::=
    nature_access_function ( branch_reference )
  | nature_access_function ( analog_net_reference [ , analog_net_reference ] )

port_probe_function_call ::=
    nature_access_function ( < analog_port_reference > )

branch_reference ::=
    hierarchical_branch_identifier
  | hierarchical_branch_identifier [ constant_expression ]
  | hierarchical_unnamed_branch_reference

hierarchical_unnamed_branch_reference ::=
    hierarchical_inst_identifier . branch ( branch_terminal [ , branch_terminal ] )
  | hierarchical_inst_identifier . branch ( < port_identifier > )
  | hierarchical_inst_identifier . branch ( < hierarchical_port_identifier > )

analog_net_reference ::=
    port_identifier
  | port_identifier [ constant_expression ]
  | net_identifier
  | net_identifier [ constant_expression ]
  | hierarchical_port_identifier
  | hierarchical_port_identifier [ constant_expression ]
  | hierarchical_net_identifier
  | hierarchical_net_identifier [ constant_expression ]

analog_port_reference ::=
    port_identifier
  | port_identifier [ constant_expression ]
  | hierarchical_port_identifier
  | hierarchical_port_identifier [ constant_expression ]

Branch or port probe function calls shall only reference nets and ports declared to belong to a continuous discipline. The nature attribute identifier for a branch probe function call must be the access function name for the potential or flow nature defined for the discipline. For a port probe function call, the nature attribute identifier must be the access function name for the flow nature, and the port reference must be a declared port of the module (not hierarchical).

module transamp(out, in);
    inout out, in;
    electrical out, in;
    parameter real gm = 1;
    analog
        I(out) <+ gm*V(in);
endmodule

module resistor(p, n);
    inout p, n;
    electrical p, n;
    branch (p,n) res;
    parameter real R = 50;
    analog
        V(res) <+ R*I(res);
endmodule

The potential and flow generic access functions can also be used:

module measure1(p);
    output p;
    electrical p;
    parameter real V = 1.1;
    analog begin
        $strobe("%M: voltage ratio is %g", potential(p) / V);
    end
endmodule

When potential and flow access functions are used on an unnamed branch composed of two nets, the discipline of both nets must be the same.

5.5.2 Signal Access for Vector Branches

Ports, nets, and branches can be arranged as vectors; however, access functions can only be applied to scalars or individual elements of a vector. The scalar element is selected with an index, e.g., V(in[1]).

The index must be a constant expression, though it may include genvar variables. Genvar variables can only be assigned as the iteration index of for loops; they allow signal access within looping constructs.

// N-bit DAC example.
module dac(out, in, clk);
    parameter integer width = 8 from [2:24];
    parameter real fullscale = 1.0, vth = 2.5, td = 1n, tt = 1n;
    output out;
    input [0:width-1] in;
    input clk;
    electrical out;
    electrical [0:width-1] in;
    electrical clk;
    real aout;
    genvar i;
    analog begin
        @(cross(V(clk) - vth, +1)) begin
            aout = 0;
            for (i = width - 1; i >= 0; i = i - 1) begin
                if (V(in[i]) > vth) begin
                    aout = aout + fullscale/pow(2, width - i);
                end
            end
        end
        V(out) <+ transition(aout, td, tt);
    end
endmodule
// 8-bit fixed-width DAC example.
module dac8(out, in, clk);
    parameter real fullscale = 1.0, vth = 2.5, td = 1n, tt = 1n;
    output out;
    input [0:7] in;
    input clk;
    electrical out;
    electrical [0:7] in;
    electrical clk;
    real aout;
    analog begin
        @(cross(V(clk) - 2.5, +1)) begin
            aout = 0;
            aout = aout + ((V(in[7]) > vth) ? fullscale/2.0 : 0.0);
            aout = aout + ((V(in[6]) > vth) ? fullscale/4.0 : 0.0);
            aout = aout + ((V(in[5]) > vth) ? fullscale/8.0 : 0.0);
            aout = aout + ((V(in[4]) > vth) ? fullscale/16.0 : 0.0);
            aout = aout + ((V(in[3]) > vth) ? fullscale/32.0 : 0.0);
            aout = aout + ((V(in[2]) > vth) ? fullscale/64.0 : 0.0);
            aout = aout + ((V(in[1]) > vth) ? fullscale/128.0 : 0.0);
            aout = aout + ((V(in[0]) > vth) ? fullscale/256.0 : 0.0);
        end
        V(out) <+ transition(aout, td, tt);
    end
endmodule

5.5.3 Accessing Attributes

Attributes are attached to the nature of a potential or flow. Attributes for a net or branch are accessed using the hierarchical referencing operator (.) to the potential or flow.

nature_attribute_reference ::=
    net_identifier . potential_or_flow . nature_attribute_identifier

potential_or_flow ::= potential | flow

This syntax shall not be used for the access, ddt_nature, or idt_nature attributes of a nature, nor any other attribute whose value is not a constant expression.

module twocap(a, b, n1, n2);
    inout a, b, n1, n2;
    electrical a, b, n1, n2;
    branch (n1, n2) cap;
    parameter real c= 1p;
    analog begin
        I(a,b) <+ c*ddt(V(a,b), a.potential.abstol);
        I(cap) <+ c*ddt(V(cap), n1.potential.abstol);
    end
endmodule

The abstol attribute of a nature may also be accessed by using the nature's identifier as the appropriate argument to ddt(), idt(), or idtmod() operators.

5.5.4 Creating Unnamed Branches Using Hierarchical Net References

An access function in a module can have one or more hierarchical net references to nets in other module instances. In these cases, a new unnamed branch is created in the module containing the access function call.

module signal_monitor;
    parameter refv = 2.3;
    electrical a;
    analog begin
        V(a) <+ refv;
        // Creates an unnamed branch between top.drv.a and implicit ground.
        $strobe("voltage at top.drv.a = %g volts", V(top.drv.a));
        // Creates an unnamed branch between top.drv.a and top.drv.b
        $strobe("voltage diff in top.drv = %g volts", V(top.drv.a, top.drv.b));
        // Creates an unnamed branch between local net a and top.drv.a
        $strobe("voltage diff from ref in top.drv = %g volts", V(a,top.drv.a));
        // References the unnamed branch created in the first $strobe
        if(V(top.drv.a) > 10.0) $strobe("voltage limit exceeded at top.drv.a");
    end
endmodule

Even if the instance top.drv already has an unnamed branch between nodes a and ground and a and b, the new unnamed branches are created in the module signal_monitor.

5.5.5 Accessing Nets and Branch Signals Hierarchically

A module is allowed to access the potential and flow of a branch in another module instance using an access function, provided that value is available in the other instance. An error shall be reported if unavailable. Reasons for unavailability:

  • The branch does not exist in the other instance
  • The access function is not the valid access function for that named branch
module top;
    A a1();
    B b1();
endmodule

module A;
    electrical n,p;
    branch (n,p) b;
    analog V(b) <+ 1.34;
endmodule

module B;
    analog $strobe("voltage == %g", V(top.a1.b));
endmodule

To access an existing unnamed branch in another module instance, use the hierarchical_unnamed_branch_reference syntax:

analog begin
    // Voltage of unnamed branch between nets a and b in top.drv.
    $strobe("Voltage == %g", V(top.drv.branch(a,b)));
    // Current through unnamed port branch for port p in top.drv
    $strobe("Current == %g", I(top.drv.branch(<p>)));
end

5.6 Contribution Statements

The branch contribution statement is used in the analog block to describe continuous-time behavior between a module's analog nets and ports. Contribution statements may be described in direct or indirect form.

5.6.1 Direct Branch Contribution Statements

The direct contribution statement uses the branch contribution operator <+ to describe the mathematical relationship between one or more analog nets within the module.

contribution_statement ::= branch_lvalue <+ analog_expression ;

branch_lvalue ::= branch_probe_function_call

branch_probe_function_call ::=
    nature_access_function ( branch_reference )
  | nature_access_function ( analog_net_reference [ , analog_net_reference ] )

The right-hand side can be any combination of linear, nonlinear, or differential expressions of module signals, constants, and parameters which evaluates to or can be promoted to a real value. The left-hand side specifies the source branch signal and shall consist of a signal access function applied to a branch.

If the contribution statement is conditionally executed, the expression shall not include an analog filter function unless the conditional expression is a constant expression.

Contributions cannot be made to an analog port declared with an input direction, but an output port can be accessed. There shall be no contributions to an implicit net; contributions shall be done only on analog nets declared with a continuous discipline.

module resistor(p, n);
    inout p, n;
    electrical p, n;
    branch (p,n) path;          // named branch
    parameter real r = 0;
    analog
        V(path) <+ r*I(path);
endmodule

module capacitor(p, n);
    inout p, n;
    electrical p, n;
    parameter real c = 0;
    analog
        I(p,n) <+ c*ddt(V(p, n)); // unnamed branch p,n
endmodule

The potential and flow generic access functions can also be used for contributions:

module measure2(p);
    output p;
    electrical p;
    parameter real V = 1.1;
    parameter real I = 1u;
    parameter real R = 10k;
    analog begin
        potential(p) <+ flow(p) * R;   // create a resistor
        $strobe("voltage ratio at port 'p' is %g", potential(p) / V);
        $strobe("current ratio through port 'p' is %g", flow(<p>) / I);
    end
endmodule

5.6.1.1 Relations

Branch contribution statements implicitly define source branch relations. The branch is directed from the first net of the access function to the second net. If the second net is not specified, the global reference node (ground) is used.

Each net has two quantities: potential and flow. Each branch has two quantities: potential across and flow through.

module amp(out, in);
    input in;
    output out;
    electrical out, in;
    parameter real Gain = 1;
    analog
        V(out) <+ Gain*V(in);
endmodule

5.6.1.2 Evaluation

A statement is evaluated as follows for source branch contributions:

  1. The simulator evaluates the right-hand side.
  2. The simulator adds the value of the right-hand side to any previously retained value of the branch for later assignment. If there are no previously retained values, the value itself is retained.
  3. At the end of the simulation cycle, the simulator assigns the retained value to the source branch.

Parasitics are added by simply adding additional contribution statements:

module amp(out, in);
    inout out, in;
    electrical out, in;
    parameter real Gain = 1, Rin = 1, Cin = 1, Rout = 1, Lout = 1;
    analog begin
        // gain of amplifier
        V(out) <+ Gain*V(in);
        // model input admittance
        I(in) <+ V(in)/Rin;
        I(in) <+ Cin*ddt(V(in));
        // model output impedance
        V(out) <+ Rout*I(out);
        V(out) <+ Lout*ddt(I(out));
    end
endmodule

5.6.1.3 Value Retention

Multiple contributions to the same potential branch or same flow branch will be additive. However:

  • Contributing a flow to a branch which already has a value retained for the potential results in the potential being discarded and the branch being converted to a flow source.
  • Contributing a potential to a branch which already has a value retained for the flow results in the flow being discarded and the branch being converted to a potential source.

Unlike variables, the contributed value for a branch is only valid for the current iteration. If a branch is not contributed to (directly or indirectly) for any particular iteration, and it is not a branch probe, it shall be treated as a flow source with a value of 0.

// Value retention: equivalent forms
if (closed)
    V(p,n) <+ 0;

// is equivalent to:
if (closed)
    V(p,n) <+ 0;
else
    I(p,n) <+ 0;
// Value retention rules: result is V(p,n) = 7.0
module value_ret(p, n);
    inout p, n;
    electrical p, n;
    analog begin
        V(p,n) <+ 1.0; // no previously-retained value, 1 is retained
        I(p,n) <+ 2.0; // potential discarded; flow of 2 retained
        V(p,n) <+ 3.0; // flow discarded; potential of 3 retained
        V(p,n) <+ 4.0; // 4 added to previously-retained 3
    end
endmodule
// Current-controlled current source: I(ps,ns) is a flow probe (potential is zero)
module cccs (p, n, ps, ns);
    inout p, n, ps, ns;
    electrical p, n, ps, ns;
    parameter real A = 1.0;
    analog begin
        I(p,n) <+ A * I(ps,ns);
    end
endmodule

5.6.2 Examples: Four Controlled Sources

module control_source (p, n, ps, ns);
    inout p, n, ps, ns;
    electrical p, n, ps, ns;
    parameter A=1;
    branch (ps,ns) in;
    branch (p,n) out;
    analog begin
        // add one behavioral statement from below
    end
endmodule

5.6.3 Resistor and Conductor

// Linear conductor
module my_conductor(p,n);
    inout p, n;
    electrical p,n;
    parameter real G=1;
    branch (p,n) cond;
    analog begin
        I(cond) <+ G * V(cond);
    end
endmodule

The assignment to I(cond) makes cond a current source branch; V(cond) accesses the potential probe built into the current source branch.

// Linear resistor
module my_resistor(p,n);
    inout p,n;
    electrical p,n;
    parameter real R=1;
    branch (p,n) res;
    analog begin
        V(res) <+ R * I(res);
    end
endmodule

The assignment to V(res) makes res a potential source branch; I(res) accesses the flow probe built into the potential source branch.

5.6.4 RLC Circuits

Series RLC circuit (summing voltages):

V(p, n) <+ R*I(p, n) + L*ddt(I(p, n)) + idt(I(p, n))/C;

Parallel RLC circuit (summing currents):

I(p, n) <+ V(p, n)/R + C*ddt(V(p, n)) + idt(V(p, n))/L;

5.6.5 Switch Branches

Contribution to a branch may be switched between potential and flow during a simulation. This is useful for modeling ideal switches and mechanical stops.

Contribution statements are allowed within conditional statements but are not allowed within event control statements. The contribution statements shall not use analog operators when the condition can change during the course of a simulation.

module relay (p, n, cp, cn);
    inout p, n, cp, cn;
    electrical p, n, cp, cn;
    branch (p,n) out;
    branch (cp,cn) ctrl;
    parameter real thresh = 0;
    analog begin
        @(cross(V(ctrl) - thresh, 0))
            ; // acts only to resolve threshold crossings
        if (V(ctrl) > thresh)
            V(out) <+ 0;
        else
            I(out) <+ 0; // optional due to value retention
    end
endmodule

A discontinuity of order zero (0) is assumed to occur when the branch switches; it is not necessary to use $discontinuity with switch branches. Contribution statements inside event control statements are disallowed because they may not be executed at every timepoint.

5.6.6 Implicit Contributions

The value of the target may be expressed in terms of itself. This is referred to as an implicit or fixed-point formulation.

I(diode) <+ is*(limexp((V(diode) - r*I(diode))/$vt) - 1);

I(diode) appears on both sides of the contribution operator. The simulator will find the value of I(diode) that equals the sum of the contributions made to it, even if the contributions are a function of I(diode) itself.

5.6.7 Indirect Branch Contribution Statements

Indirect branch contributions provide an alternative to direct contributions, useful when direct contributions do not behave as needed. The syntax reads as "drive target so that equation == value".

For the ideal opamp (nullor), the constitutive equation is vin = 0:

V(out) : V(pin,nin) == 0;

This indicates out is driven with a voltage source, and the source voltage must be adjusted so that V(pin,nin) == 0. Any branches referenced in the equation are only probed, not driven.

The tolerance for the equation is taken from the argument on the left side of the equality operator (in this case V(pin,nin)).

indirect_contribution_statement ::=
    branch_lvalue : indirect_expression == analog_expression ;

indirect_expression ::=
    branch_probe_function_call
  | port_probe_function_call
  | ddt ( branch_probe_function_call [ , abstol_expression ] )
  | ddt ( port_probe_function_call [ , abstol_expression ] )
  | idt ( branch_probe_function_call [ , analog_expression
        [ , analog_expression [ , abstol_expression ] ] ] )
  | idt ( port_probe_function_call [ , analog_expression [ , analog_expression
        [ , abstol_expression ] ] ] )
  | idtmod ( branch_probe_function_call [ , analog_expression [ , analog_expression
        [ , analog_expression [ , abstol_expression ] ] ] ] )
  | idtmod ( port_probe_function_call [ , analog_expression [ , analog_expression
        [ , analog_expression [ , abstol_expression ] ] ] ] )

branch_lvalue ::= branch_probe_function_call

The left-hand side of the equality operator must be an access function, or ddt, idt, or idtmod applied to an access function.

Indirect branch contributions shall not be used in conditional or looping statements unless the conditional expression is a constant expression. The constant expression shall not include the analysis() function with an argument that can result in different return values during a single analysis (such as "ic" or "nodeset").

module opamp(out, pin, nin);
    inout out, pin, nin;
    electrical out, pin, nin;
    analog
        V(out) : V(pin,nin) == 0;
endmodule

5.6.7.1 Multiple Indirect Contributions

For multiple indirect contribution statements, the targets frequently can be paired with any equation:

V(x) : ddt(V(x)) == f(V(x), V(y), V(z));
V(y) : ddt(V(y)) == g(V(x), V(y), V(z));
V(z) : ddt(V(z)) == h(V(x), V(y), V(z));

The pairing of targets to equations can be rearranged without affecting the results:

V(y) : ddt(V(x)) == f(V(x), V(y), V(z));
V(z) : ddt(V(y)) == g(V(x), V(y), V(z));
V(x) : ddt(V(z)) == h(V(x), V(y), V(z));

5.6.7.2 Indirect and Direct Contribution

Indirect contribution statements are incompatible with direct contribution statements across the same pair of analog nets (or any of its parallel branches). Once a value is indirectly assigned to a branch, it cannot be contributed to using the branch contribution operator <+.

5.6.8 Contributing Hierarchically

5.6.8.1 Contributions to Branches Between Hierarchical Nets

Direct contribution statements can contribute to a branch between combinations of local and hierarchical nets. A new unnamed branch is created in the module containing the direct contribution statements.

module source_driver();
    electrical m;
    parameter real vref = 0.0;
    analog begin
        V(m) <+ vref;
        // Creates unnamed voltage source branch of 1.8V
        // between top.drv.x and implicit ground.
        V(top.drv.x) <+ 1.8;
        // Creates unnamed voltage source branch of 1.2V
        // between top.drv.x and top.drv.y
        V(top.drv.x, top.drv.y) <+ 1.2;
        // Creates unnamed voltage source branch of 0.9V
        // between local net m and top.drv.y
        V(m, top.drv.y) <+ 0.9;
    end
endmodule

The simulator shall check if the contribution produces a solvable set of equations (e.g., no voltage source loops).

5.6.8.2 Hierarchical Direct Contributions to Branches

Hierarchical direct contributions to named and unnamed branches are allowed provided the branch is suitable. Reasons a hierarchical branch contribution would not be allowed:

  • Invalid access function used for the contribution to the particular branch
  • The hierarchical contribution changes the branch into a switch branch
module source_driver();
    analog begin
        // Contributes 1.8 volts to the named branch br_v in top.drv
        V(top.drv.br_v) <+ 1.8;
        // Contributes 1.2 volts to unnamed branch between x and y in top.drv
        V(top.drv.branch(x,y)) <+ 1.2;
        // Contributes 1mA to the named branch br_i in top.drv
        I(top.drv.br_i) <+ 1m;
    end
endmodule

Hierarchical contributions are not allowed to branches that have been indirectly contributed to.

5.7 Analog Procedural Assignments

Analog procedural assignments modify analog integer, real, and string variables including array variables.

analog_procedural_assignment ::= analog_variable_assignment ;

analog_variable_assignment ::=
    scalar_analog_variable_assignment
  | array_analog_variable_assignment

scalar_analog_variable_assignment ::=
    scalar_analog_variable_lvalue = analog_expression

analog_variable_lvalue ::=
    variable_identifier
  | variable_identifier [ analog_expression ] { [ analog_expression ] }

array_analog_variable_assignment ::=
    array_analog_variable_lvalue = array_analog_variable_rvalue ;

array_analog_variable_rvalue ::=
    array_variable_identifier
  | array_variable_identifier [ analog_expression ] { [ analog_expression ] }
  | assignment_pattern

Rules for scalar variable assignments:

  • The left-hand side shall be scalar: an integer, real, or string identifier, or an element of such an array.
  • The right-hand side can be any arbitrary expression from legal operands and operators that evaluates to a scalar.
  • Concatenation expressions cannot be used as part of the analog expression.
  • Analog filter functions cannot be used if the statement is conditionally executed during simulation.
  • Hierarchical assignment of a variable from another scope/module is not allowed.

Rules for unpacked array variable assignments:

  • The array on the LHS shall be an array variable, a slice, or an array parameter (when the default value is assigned).
  • Both LHS and RHS must be unpacked.
  • Array assignments shall only be done with compatible arrays: element types must be equivalent and every dimension must have the same number of elements.

5.8 Analog Conditional Statements

5.8.1 if-else-if Statement

The if-else statement determines whether a statement is executed. If any conditionally-executed statement contains an analog operator, the conditional expression shall be an analysis_or_constant_expression.

analog_conditional_statement ::=
    if ( analog_expression ) analog_statement_or_null
    { else if ( analog_expression ) analog_statement_or_null }
    [ else analog_statement_or_null ]

If the expression evaluates to true (non-zero), the true-branch statements execute. If it evaluates to false (zero), the else-branch statements execute (if present).

The following two statements express the same logic:

if (expression)
if (expression != 0)

Since the else part is optional, an omitted else in a nested if sequence is resolved by always associating the else with the closest previous if which lacks an else:

if (index > 0)
    if (i > j)
        result = i;
    else             // else applies to inner if
        result = j;

To force a different association, use begin-end:

if (index > 0) begin
    if (i > j)
        result = i;
end
else result = j;

5.8.3 Case Statement

The case statement tests if an expression matches one of a number of other expressions and branches accordingly.

analog_case_statement ::=
    case ( analog_expression ) analog_case_item { analog_case_item } endcase
  | casex ( analog_expression ) analog_case_item { analog_case_item } endcase
  | casez ( analog_expression ) analog_case_item { analog_case_item } endcase

analog_case_item ::=
    analog_expression { , analog_expression } : analog_statement_or_null
  | default [ : ] analog_statement_or_null
  • The default statement is optional. Multiple default statements in one case statement is illegal.
  • Neither the case expression nor the case item expressions are required to be constant.
  • Case item expressions are evaluated and compared in the exact order given. The first match triggers execution.
  • If all comparisons fail and a default item is given, the default item statement executes; otherwise none execute.

5.8.4 Restrictions on Conditional Statements

  • Analog filter functions are restricted inside conditional statements (if-else-if and case) unless the conditional expression is a constant expression.
  • For analog filter functions, the conditional statements cannot be nested conditionally.
  • Contribution statements are allowed as part of conditional analog statements (switch branches).
  • Event control statements (timer, cross, etc.) cannot be used inside conditional statements unless the conditional expression is a constant expression.

5.9 Looping Statements

Three types of looping statements: repeat, while, and for.

The following restrictions apply to repeat, while, and for loops (but not to analog for statements):

  • Analog filter functions are not allowed
  • Event control statements are not allowed
  • Contribution statements are not allowed

5.9.1 Repeat and While Statements

repeat() executes a statement a fixed number of times. The expression determines how many times.

while() executes a statement until an expression becomes false. If the expression starts out false, the statement is not executed at all.

The repeat and while expressions shall be evaluated once before the execution of any statement to determine the number of times the statements are executed.

analog_loop_statement ::=
    repeat ( analog_expression ) analog_statement
  | while ( analog_expression ) analog_statement
  ...

5.9.2 For Statements

analog_loop_statement ::=
    ...
  | for ( analog_variable_assignment ; analog_expression ; analog_variable_assignment )
        analog_statement

The for() statement controls execution via a three-step process:

  1. It executes an assignment normally used to initialize an integer which controls the number of loops.
  2. It evaluates an expression -- if the result is zero (0), the for-loop exits; otherwise, it executes its associated statement(s) and then performs Step 3.
  3. It executes an assignment normally used to modify the loop-control variable, then repeats Step 2.

5.9.3 Analog For Statements

The analog for statements are syntactically equivalent to for() statements except the associated analog statement can contain analog operators. The additional restriction is that the procedural assignment and conditional expressions must be statically evaluatable. Verilog-AMS HDL provides genvar-derived expressions for this purpose.

analog_loop_generate_statement ::=
    for ( genvar_initialization ; genvar_expression ; genvar_iteration )
        analog_statement
module genvarexp(out, dt);
    parameter integer width = 1;
    output out;
    input [1:width] dt;
    electrical out;
    electrical [1:width] dt;
    genvar k;
    real tmp;
    analog begin
        tmp = 0.0;
        for (k = 1; k <= width; k = k + 1) begin
            tmp = tmp + V(dt[k]);
            V(out) <+ ddt(V(dt[k]));
        end
    end
endmodule

5.10 Analog Event Control Statements

Analog behavior can be controlled using events. Events have the following characteristics:

  • Events have no time duration
  • Events can be triggered and detected in different parts of the behavioral model
  • Events do not block the execution of an analog block
  • Events can be detected using the @ operator
  • Events do not hold any data
  • There can be both digital and analog events

Three types of analog events: global events (5.10.2), monitored events (5.10.3), and named events (5.10.4). Null arguments are not allowed in analog events.

analog_event_control_statement ::=
    analog_event_control analog_event_statement

analog_event_control ::=
    @ hierarchical_event_identifier
  | @ ( analog_event_expression )

analog_event_expression ::=
    expression
  | posedge expression
  | negedge expression
  | hierarchical_event_identifier
  | initial_step [ ( " analysis_identifier " { , " analysis_identifier " } ) ]
  | final_step [ ( " analysis_identifier " { , " analysis_identifier " } ) ]
  | analog_event_functions
  | analog_event_expression or analog_event_expression
  | analog_event_expression , analog_event_expression

analog_event_functions ::=
    cross ( analog_expression [ , analog_expression_or_null
        [ , constant_expression_or_null
            [ , constant_expression_or_null [ , analog_expression ] ] ] ] )
  | above ( analog_expression [ , constant_expression_or_null
        [ , constant_expression_or_null [ , analog_expression ] ] ] )
  | timer ( analog_expression [ , analog_expression_or_null
        [ , constant_expression_or_null [ , analog_expression ] ] ] )
  | absdelta ( analog_expression , analog_expression
        [ , constant_expression_or_null
            [ , constant_expression_or_null [ , analog_expression ] ] ] )

analog_event_statement ::=
    { attribute_instance } analog_loop_statement
  | { attribute_instance } analog_case_statement
  | { attribute_instance } analog_conditional_statement
  | { attribute_instance } analog_procedural_assignment
  | { attribute_instance } analog_event_seq_block
  | { attribute_instance } analog_system_task_enable
  | { attribute_instance } disable_statement
  | { attribute_instance } event_trigger
  | { attribute_instance } ;

The procedural statement following the event expression is executed whenever the event occurs. Analog event detection is non-blocking: execution of the procedural statement is skipped unless the analog event has occurred.

Restrictions on statements within an event control block:

  • Analog filter functions cannot be used (the statement cannot maintain its internal state since it is only executed intermittently)
  • Contribution statements cannot be used (they can generate discontinuity in analog signals)
  • Nested event control statements are not allowed

The parentheses around the event expression are required.

Verilog-AMS mixed-signal note: Analog events can also be detected within digital blocks using analog_event_functions in the digital event_expression. The usage of initial_step and final_step analog events is not allowed in the digital context.

5.10.1 Event OR Operator

The OR-ing of events indicates the occurrence of any one of the specified events shall trigger the execution of the procedural statement. The keyword or is used as the event OR operator. A comma (,) can be used interchangeably with or.

analog begin
    @(initial_step or cross(V(smpl)-2.5,+1)) begin
        vout = (V(in) > 2.5);
    end
    V(out) <+ vout;
end

Here, initial_step is a global event and cross() returns a monitored event. The variable vout is set to zero or one whenever either event occurs.

5.10.2 Global Events

Global events are generated by a simulator at various stages of simulation. The user model cannot generate these events. They are detected by using the name of the global event in an event expression with the @ operator. Global events are pre-defined and cannot be redefined.

analog_event_expression ::=
    ...
  | initial_step [ ( " analysis_identifier " { , " analysis_identifier " } ) ]
  | final_step [ ( " analysis_identifier " { , " analysis_identifier " } ) ]
  ...

initial_step and final_step generate global events on the first and last point in an analysis, respectively. final_step will also generate a global event upon termination of simulation due to $finish(). Both can take an optional argument consisting of an analysis list.

@(initial_step("ac", "dc"))  // active for dc and ac only
@(initial_step("tran"))      // active for transient only

If no analysis list is specified, initial_step is active during the first point (or initial DC analysis) of every analysis. final_step without an analysis list is active during the last point of every analysis.

Sweep refers to a dc analysis in which a parameter is swept through multiple values and an operating point analysis is performed for each value. d1 is the first point; d2 through dN are subsequent points.

module bitErrorRate (in, ref);
    input in, ref;
    electrical in, ref;
    parameter real period=1, thresh=0.5;
    integer bits, errors;
    analog begin
        @(initial_step) begin
            bits = 0;
            errors = 0;
        end
        @(timer(0, period)) begin
            if ((V(in) > thresh) != (V(ref) > thresh))
                errors = errors + 1;
            bits = bits + 1;
        end
        @(final_step)
            $strobe("bit error rate = %f%%", 100.0 * errors / bits );
    end
endmodule

5.10.3 Monitored Events

Monitored events are detected using event functions with the @ operator. Triggering is implicit due to change in signals, simulation time, or other runtime conditions.

5.10.3.1 cross Function

The cross() function generates a monitored analog event to detect threshold crossings when the expression crosses zero (0) in the specified direction. It also controls the timestep to accurately resolve the crossing.

cross ( expr [ , dir [ , time_tol [ , expr_tol [ , enable ] ] ] ] )
ArgumentTypeRequiredDescription
expranalog_expressionYesExpression to monitor for zero crossings
diranalog_expression (integer)NoDirection: 0 = both, +1 = rising, -1 = falling. Other values disable the function.
time_tolconstant_expressionNoMaximum time error at crossing. Non-negative.
expr_tolconstant_expressionNoMaximum expression error at crossing. Non-negative.
enableanalog_expressionNoIf specified and zero, cross() is inactive.

If dir is 0 or not specified, the event and timestep control occur on both positive and negative crossings. If dir is +1, only rising edges. If dir is -1, only falling edges. For any other value of dir, the function does not generate an event and does not control the timestep.

If expr_tol is specified, time_tol shall also be specified and both tolerances shall be satisfied at the crossing. If tolerances are not specified, the tool sets them. If either or both tolerances are defined, then dir shall also be defined.

The event shall occur after the threshold crossing and while the signal remains in the box defined by the actual crossing, expr_tol, and time_tol.

Analog filter functions cannot be used for dir or enable arguments.

module sh (in, out, smpl);
    parameter real thresh = 0.0;
    parameter integer dir = +1 from [-1:+1] exclude 0;
    output out;
    input in, smpl;
    electrical in, out, smpl;
    real state;
    analog begin
        @(cross(V(smpl) - thresh, dir))
            state = V(in);
        V(out) <+ transition(state, 0, 10n);
    end
endmodule

There are two ways to disable the cross function: set enable to 0, or give a value other than -1, 0, or 1 to dir:

module sh (in, out, smpl, en);
    parameter real thresh = 0.0;
    parameter integer dir = +1 from [-1:+1] exclude 0;
    output out;
    input in, smpl, en;
    electrical in, out, smpl;
    real state;
    analog begin
        @(cross(V(smpl) - thresh, dir, , , en === 1'b1))
            state = V(in);
        V(out) <+ transition(state, 0, 10n);
    end
endmodule

cross() maintains its internal state and has the same restrictions as analog operators. It shall not be used inside if, case, casex, or casez unless the conditional expression is a genvar expression. It is not allowed in repeat and while loops but is allowed in analog for statements.

5.10.3.2 above Function

The above() function is almost identical to cross(), except it also triggers during initialization or dc analysis. It generates a monitored analog event to detect when the expression crosses zero from below. It controls the timestep to accurately resolve the crossing during transient analysis.

above ( expr [ , time_tol [ , expr_tol [ , enable ] ] ] )
ArgumentTypeRequiredDescription
expranalog_expressionYesExpression to monitor
time_tolconstant_expressionNoMaximum time error. Non-negative.
expr_tolconstant_expressionNoMaximum expression error. Non-negative.
enableanalog_expressionNoIf specified and zero, above() is inactive.

Key differences from cross():

  • above() can generate an event during initialization. If the expression is positive at the conclusion of the initial condition analysis that precedes a transient analysis, it shall generate an event.
  • cross() can only generate an event after simulation time has advanced from zero.
  • cross() will not generate events for non-transient analyses (ac, dc, noise), but above() can.
  • During a dc sweep, above() shall also generate an event when the expression crosses zero from below; however, the step size of the dc sweep is not controlled.
module sh (in, out, smpl);
    output out;
    input in, smpl;
    electrical in, out, smpl;
    real state;
    analog begin
        @(above(V(smpl) - 2.5))
            state = V(in);
        V(out) <+ transition(state, 0, 10n);
    end
endmodule

above() maintains its internal state and has the same restrictions on its use as cross().

5.10.3.3 timer Function

The timer() function generates analog events to detect specific points in time.

timer ( start_time [ , period [ , time_tol [ , enable ] ] ] )
ArgumentTypeRequiredDescription
start_timeanalog_expressionYesAbsolute time of first event
periodanalog_expressionNoPeriod of subsequent events. If ≤ 0, triggers only once.
time_tolconstant_expressionNoMaximum time error. Non-negative.
enableanalog_expressionNoIf specified and zero, timer() is inactive.

The timer() function schedules an event at an absolute time (start_time). The simulator places a time point within time_tol of the event. If time_tol is not specified, the default time point is at, or just beyond, the time of the event.

If period is greater than zero, the timer schedules subsequent events at multiples of period. If period evaluates to a value less than or equal to 0.0, the timer triggers only once at the specified start_time (if the start_time is in the future).

If start_time or period expressions change value during evaluation of the analog block, the next event will be scheduled based on the latest value.

If enable is specified and zero, timer() is inactive and does not generate events as long as enable is zero. It will start generating events once enable returns to nonzero as if it had never been disabled.

Analog filter functions cannot be used for the start_time and period arguments.

module bitStream (out);
    output out;
    electrical out;
    parameter period = 1.0;
    integer x;
    analog begin
        @(timer(0, period))
            x = $random + 0.5;
        V(out) <+ transition( x, 0.0, period/100.0 );
    end
endmodule

5.10.3.4 absdelta Function

The absdelta event function generates an event when an analog expression changes more than a specified amount. It is particularly useful for discretizing analog signals.

Verilog-AMS note: The absdelta function is only allowed in an initial or always block of a Verilog-AMS module (digital context). 
absdelta ( expr , delta [ , time_tol [ , expr_tol [ , enable ] ] ] )
ArgumentTypeRequiredDescription
expranalog_expressionYesExpression to monitor
deltaanalog_expressionYesChange threshold. Non-negative.
time_tolconstant_expressionNoMaximum time error. Non-negative.
expr_tolconstant_expressionNoLargest negligible difference. Non-negative.
enableanalog_expression (integer)NoIf specified and zero, absdelta() is inactive.

absdelta() does not force timesteps in the analog solver; it observes the expr argument and generates events at appropriate times. It may interpolate event times to avoid forcing analog timesteps.

absdelta() generates events for:

  • During initialization or dc sweep analysis
  • When the enable argument changes from zero to non-zero
  • When the expr value changes in absolute value by more than delta, relative to the previous absdelta() event (but not when the current time is within time_tol of the previous event). The event may be scheduled at any time between the interpolated absolute change of (delta - expr_tol) and (delta + expr_tol).
  • When expr changes direction (but not when the change amount is less than expr_tol)

If delta is set to zero, an event is generated every timestep the expression value changes, with zero tolerances. expr_tol and time_tol, if specified, will be ignored. No events are generated by interpolation. Setting delta to zero should be done with great care as it may severely impact simulation performance.

A time_tol smaller than the time precision is ignored and the time precision is used instead.

`include "disciplines.vams"
`timescale 1ns / 100ps
module electrical_sampler (e_in, r_out);
    input e_in;
    output r_out;
    electrical e_in;
    wreal r_out;
    parameter real vdelta=0.1 from (0:inf);   // voltage delta
    parameter real ttol=1n from (0:1m];       // time tolerance
    parameter real vtol=0.01 from (0:inf);    // voltage tolerance
    real sampled;
    assign r_out = sampled;
    always @(absdelta(V(e_in), vdelta, ttol, vtol))
        sampled = V(e_in);
endmodule

5.10.4 Named Events

An identifier declared as an event data type is called a named event. A named event is triggered explicitly and used in an event expression to control the execution of procedural statements.

Named events can be triggered from always and initial blocks, or from an analog event statement.

An event name shall be declared explicitly before use:

event_declaration ::= event list_of_event_identifiers ;

list_of_event_identifiers ::=
    event_identifier { dimension } { , event_identifier { dimension } }

dimension ::=
    [ dimension_constant_expression : dimension_constant_expression ]

A declared event is triggered with the event triggering statement:

event_trigger ::=
    -> hierarchical_event_identifier { [ expression ] } ;

An event-controlled statement (e.g., @trig rega = regb;) causes simulation of its containing procedure to wait until some other procedure executes the appropriate event-triggering statement (e.g., -> trig).

5.10.5 Digital Events in Analog Behavior

Verilog-AMS mixed-signal feature: To model mixed-signal functionality, analog behavior can be made sensitive to digital events, including posedge events, negedge events, state change events, and named events. This is a Verilog-AMS mixed-signal capability and is not part of the pure Verilog-A subset.
