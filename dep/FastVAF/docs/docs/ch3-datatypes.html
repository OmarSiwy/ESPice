Chapter 3: Data Types

3.1 Overview

Verilog-AMS HDL supports integer, genvar, real, and parameter data types as found in IEEE Std 1364-2005 Verilog HDL. It includes the string data type defined by IEEE Std 1800-2012 SystemVerilog. It also modifies the parameter data types and introduces array of real as an extension of the real data type. It extends the net data types to support a new type called wreal to model real value nets.

Verilog-AMS HDL introduces a new data type, called net_discipline, for representing analog nets and declaring disciplines of all nets and regs. The disciplines define the domain and the natures of potential and flow and their associated attributes for continuous domains.

3.2 Integer and Real Data Types

integer_declaration ::= integer list_of_variable_identifiers ;

real_declaration ::= real list_of_real_identifiers ;

list_of_real_identifiers ::= real_type { , real_type }

list_of_variable_identifiers ::= variable_type { , variable_type }

real_type ::=
    real_identifier { dimension } [ = constant_arrayinit ]
  | real_identifier = constant_expression

variable_type ::=
    variable_identifier { dimension } [ = constant_arrayinit ]
  | variable_identifier = constant_expression

dimension ::= [ dimension_constant_expression : dimension_constant_expression ]

An integer declaration declares one or more variables of type integer. These variables can hold values ranging from -231 to 231-1. Arrays of integers can be declared using a range which defines the upper and lower indices of the array. Both indices shall be constant expressions and shall evaluate to a positive integer, a negative integer, or zero.

Arithmetic operations performed on integer variables produce 2's complement results.

A real declaration declares one or more variables of type real. The real variables are stored as 64-bit quantities, as described by IEEE Std 754-1985 (double precision floating point numbers).

Arrays of parameter can be declared using a range which defines the upper and lower indices of the array. Both indices shall be constant expressions and shall evaluate to a positive integer, a negative integer, or zero.

Integers are initialized at the start of a simulation depending on how they are used. Integer variables whose values are assigned in an analog context default to an initial value of zero (0). Real variables are initialized to zero (0) at the start of a simulation.

integer a[1:64];                 // an array of 64 integer values
real float;                      // a variable to store real value
real gain_factor[1:30];          // array of 30 gain multipliers
                                 // with floating point values
integer flag_array[0:8][0:3];    // a multidimensional integer array
real vtable[0:16][0:7][0:64];    // a multidimensional real array

3.2.1 Output Variables

The standard attributes for descriptions and units have a special meaning for variables declared at module scope. Module scope variables with a desc or units attribute, or both, shall be known as output variables, and simulators shall provide access to their values.

(* desc="gate-source capacitance", units="F" *)
real cgs;

An operating-point display from the simulator might include:

cgs = 4.21e-15 F gate-source capacitance

Units and descriptions specified for block-level variables shall be ignored by the simulator, but can be used for documentation purposes.

3.3 String Data Type

The string data type is an ordered collection of characters. The length of a string variable is the number of characters in the collection. Variables of type string are dynamic as their length may vary during simulation.

String literals behave like packed arrays of a width that is a multiple of 8 bits. A string literal assigned to a packed array of an integral variable of a different size is either truncated to the size of the variable or padded with zeroes to the left as necessary.

When using the string data type instead of an integral variable, strings can be of arbitrary length and no truncation occurs. Literal strings are implicitly converted to the string type when assigned to a string type or used in an expression involving string type operands.

String variables can take the special value "", the empty string. A string shall not contain the special character "\0".

The syntax to declare a string:

string variable_name [ = initial_value ] ;

Where variable_name is a valid identifier and the optional initial_value can be a string literal, "" for an empty string, or a string type constant expression such as a string parameter. If an initial value is not specified, the variable is initialized to "".

parameter string default_name = "John Smith";
string myName = default_name;

Arrays and multidimensional arrays of string are supported:

string names[1:3] = '{"first", "middle", "last"};
string paths[0:2][0:1] =
    '{ '{"dir1", "fileA"}, '{"dir2", "fileA"},'{"dir1","fileB"}};

A string literal can be assigned to a string or an integral type. If their size differs, the literal is right justified and either truncated on the left or zero filled on the left:

reg [8*4:1] h = "hello";   // assigns to h "ello"
reg [10:0] a = "A";        // assigns to a 'b000_0100_0001

A string literal assigned to a string variable is converted: all "\0" characters are removed; if the result is an empty string literal, the string is assigned the empty string; otherwise, the string is assigned the remaining characters.

string s1 = "hello\0world"; // sets s1 to "helloworld"
reg [15:0] r;
integer i = 1;
string b = "";
string a = {"Hi", b};
b = "Hi";              // OK
b = {5{"Hi"}};         // OK
a = {i{"Hi"}};         // OK (non constant replication)
r = {i{"Hi"}};         // invalid (non constant replication)
a = {i{b}};            // OK
a = {a,b};             // OK
a = {"Hi",b};          // OK
r = {"H",""};          // yields "H\0". "" is converted to 8'b0
b = {"H",""};          // yields "H". "" is the empty string

3.4 Parameters

local_parameter_declaration ::=
    localparam [ signed ] [ range ] list_of_param_assignments
  | localparam parameter_type list_of_param_assignments

parameter_declaration ::=
    parameter [ signed ] [ range ] list_of_param_assignments
  | parameter parameter_type list_of_param_assignments

specparam_declaration ::= specparam [ range ] list_of_specparam_assignments ;

parameter_type ::= integer | real | realtime | time | string

aliasparam_declaration ::= aliasparam parameter_identifier = parameter_identifier ;

list_of_param_assignments ::= param_assignment { , param_assignment }

param_assignment ::=
    parameter_identifier = constant_mintypmax_expression { value_range }
  | parameter_identifier range = constant_arrayinit { value_range }

range ::= [ msb_constant_expression : lsb_constant_expression ]

value_range ::=
    value_range_type ( value_range_expression : value_range_expression )
  | value_range_type ( value_range_expression : value_range_expression ]
  | value_range_type [ value_range_expression : value_range_expression )
  | value_range_type [ value_range_expression : value_range_expression ]
  | value_range_type '{ string { , string } }
  | exclude constant_expression

value_range_type ::= from | exclude

value_range_expression ::= constant_expression | -inf | inf

The list of parameter assignments shall be a comma-separated list of assignments, where the right hand side (the initializer) shall be a constant expression containing only constant numbers and previously defined parameters.

For parameters defined as arrays, the initializer shall be a constant_param_arrayinit expression which is a list of constant expressions using an assignment pattern (within '{ and } delimiters).

Parameters represent constants; it is illegal to modify their value at runtime. However, parameters can be modified at compilation time to have values different from those specified in the declaration assignment. A parameter can be modified with the defparam statement or in the module instance statement.

There are three fundamental extensions to the parameter declarations defined in IEEE Std 1364-2005:

  • A range of permissible values can be defined for each parameter.
  • Parameter arrays of basic integer and real data types can be specified.
  • String parameters may be declared.

3.4.1 Type Specification

The parameter declaration can contain an optional type specification. A default value shall be specified.

parameter real slew_rate = 1e-3;
parameter integer size = 16;

If the type is not specified, it is derived from the type of the final value assigned to the parameter, after any value overrides have been applied. The type of a string parameter and any array parameter is mandatory.

If the type is specified as integer or real, and the assigned value conflicts with the type, the value is converted to the type of the parameter. No conversion shall be applied for strings; it shall be an error to assign a numeric value to a parameter declared as string or to assign a string value to a real parameter.

parameter real size = 10;   // size is coerced to 10.0

3.4.2 Value Range Specification

A parameter declaration can contain optional specifications of the permissible range of values. More than one range can be specified for inclusion or exclusion.

Brackets [ and ] indicate inclusion of the end points. Parentheses ( and ) indicate exclusion. Mixed forms [ ) and ( ] are permitted. The first expression in the range shall be numerically smaller than the second.

parameter real neg_rail = -15 from [-50:0);
parameter integer pos_rail = 15 from (0:50);
parameter real gain = 1 from [1:1000];

The keyword inf indicates infinity. Preceded by a negative sign, it indicates negative infinity.

parameter real val3=0 from [0:inf) exclude (10:20) exclude (30:40];

A single value can be excluded:

parameter real res = 1.0 exclude 0;

Range checking applies to the value of the parameter for the instance, not against the default values. It shall be an error only if the value is out of range during simulation.

Valid values of string parameters use from with a list of valid string values, or exclude with a list of invalid values. The list is constructed using an assignment pattern ('{ }), items separated by commas:

parameter string transistortype = "NMOS" from '{ "NMOS", "PMOS" };
parameter string filename = "output.dat" exclude '{ "" };

3.4.3 Parameter Units and Descriptions

The standard attributes desc and units can be used for parameters:

(* desc="Resistance", units="Ohms" *)
parameter real res = 1.0 from [0:inf);

Units and descriptions are for documentation only; no dimensional analysis is performed. Units and descriptions specified for block-level parameters shall be ignored by the simulator.

3.4.4 Parameter Arrays

Parameter arrays have the following restrictions (failure results in an error):

  • The type of a parameter array shall be given in the declaration.
  • An array assigned to a module instance to override the default value shall be of the exact size of the parameter array.
  • Since the array range may depend on previously-declared parameters, the array size may be changed by overriding the appropriate parameters. If the array size is changed, the parameter array shall be assigned an array of the new size from the same module as the parameter assignment that changed the size.
parameter real poles[0:3] = '{ 1.0, 3.198, 4.554, 2.00 };

3.4.5 Local Parameters

Local parameters, identified by the localparam keyword, are identical to parameters except they cannot directly be modified with the defparam statement or by ordered or named parameter value assignment. Local parameters can be assigned to a constant expression containing a parameter which can itself be modified.

3.4.6 String Parameters

String parameters can be declared. Strings are useful for parameters that act as flags, where the correspondence between numerical values and the flag values may not be obvious. The set of allowed values can be specified as a comma-separated list of strings inside curly braces. String parameters may be used with the string operators listed in Table 3-3.

module ebersmoll (c,b,e);
    inout c, b, e;
    electrical c, b, e;
    parameter string transistortype = "NPN" from '{ "NPN", "PNP" };
    parameter real alphaf = 0.99 from (0:inf);
    parameter real alphar = 0.5 from (0:inf);
    parameter real ies = 1.0e-17 from (0:inf);
    parameter real ics = 1.0e-17 from (0:inf);
    real sign, ifor, irev;
    analog begin
        sign = (transistortype == "NPN") ? 1.0 : -1.0;
        ifor = ies * (limexp(sign*V(b,e)/$vt)-1);
        irev = ics * (limexp(sign*V(b,c)/$vt)-1);
        I(b,e) <+ sign*(ifor - alphar * irev);
        I(b,c) <+ sign*(irev - alphaf * ifor);
    end
endmodule

3.4.7 Parameter Aliases

Aliases can be defined for parameters using aliasparam. This allows an alternate name to be used when overriding module parameter values.

Rules:

  • The type (real, integer, or string) and range of an alias are determined by the original parameter.
  • The alias identifier shall not occur anywhere else in the module; it shall not conflict with a different parameter identifier. The equations in the module shall reference the parameter by its original name, not the alias.
  • Multiple aliases can point to the same parameter.
  • It shall be an error to specify an override for a parameter by its original name and one or more aliases, or by more than one alias, regardless of how the override is done.
  • When the simulator generates a list of parameter values, only the original name shall appear.
parameter real dtemp = 0 from [-'P_CELSIUS0:inf);
aliasparam trise = dtemp;

Valid instantiations:

nmos2 #(.trise(5)) m1(.d(d), .g(g), .s(s), .b(b));
nmos2 #(.dtemp(5)) m2(.d(d), .g(g), .s(s), .b(b));

Error (override specified for both parameter and alias):

nmos2 #(.trise(5), .dtemp(5)) m3(.d(d), .g(g), .s(s), .b(b)); //error

Parameter aliases may also be declared for hierarchical parameter system functions:

aliasparam m = $mfactor;

3.4.8 Multidimensional Parameter Array Examples

module test;
    electrical out[0:2];
    electrical in[0:2];
    crosstalk #(.c('{'{0.0,0.1,0.1},'{0.1,0.0,0.1},'{0.1,0.1,0.0}}))
        C1(out,in,1'b1);
    gen G1(in);
    sink S1(out);
endmodule

module crosstalk(out, in, distort_enable);
    input in[0:2];
    input distort_enable;
    output out[0:2];
    // A multidimensional real parameter array for channel coupling
    parameter real c[0:2][0:2] =
        '{'{0.0,0.2,0.2},'{0.2,0.0,0.2},'{0.2,0.2,0.0}};
    electrical in[0:2];
    electrical out[0:2];
    // Multidimensional real variable initialized with assignment pattern
    real distort[0:2][0:2] = '{ 3{ '{3{0.0}}}};
    // Multidimensional string to flag excessive distortion
    string above_0p5[0:2][0:2] = '{ 3{ '{3{" "}}}};
    real in_val[0:2];
    integer ii, jj;
    analog begin
        in_val = '{V(in[0]),V(in[1],V(in[2])};
        if (distort_enable) begin
            for( ii=0; ii <= 2; ii++ ) begin
                for (jj=0; jj<= 2; jj++ ) begin
                    distort[ii][jj] = c[ii][jj]*in_val[jj];
                    if (distort[ii][jj] > 0.1)
                        above_0p5[ii][jj] = "*";
                end
            end
        end
        V(out[0]) <+ in_val[0]
            + distort[0][1] + distort[0][2];
        V(out[1]) <+ distort[1][0] + in_val[1]
            + distort[1][2];
        V(out[2]) <+ distort[2][0] + distort[2][1] + in_val[2];
        @(final_step) begin
            $display("Table of distortions greater than 0.5");
            $display("#012");
            for( ii=0; ii <= 2; ii++ ) begin
                $write("%0d",ii);
                for (jj=0; jj<= 2; jj++ ) begin
                    $write(above_0p5[ii][jj]);
                end
                $display;
            end
        end
    end
endmodule

3.5 Genvars

Genvars are integer-valued variables which compose static expressions for instantiating structure behaviorally, such as accessing analog signals within behavioral looping constructs.

genvar_declaration ::= genvar list_of_genvar_identifiers ;

list_of_genvar_identifiers ::= genvar_identifier { , genvar_identifier }

The static nature of genvar variables is derived from the limitations upon the contexts in which their values can be assigned.

genvar i;
analog begin
    ...
    for (i = 0; i < 8; i = i + 1) begin
        V(out[i]) <+ transition(value[i], td, tr);
    end
    ...
end

The genvar variable i can only be assigned within the for-loop control. Assignments to the genvar variable can consist only of expressions of static values (parameters, literals, and other genvar variables).

3.6 Net Discipline

The net_discipline data type is used to declare analog nets, as well as declaring the domains of digital nets and regs. A signal can be digital, analog, or mixed, and is a hierarchical collection of nets which are contiguous (because of port connections). For analog and mixed signals, a single node is associated with all continuous net segments of the signal.

A net is characterized by the discipline it follows. A discipline is a user-defined type for declaring a net. A discipline is characterized by the domain and the attributes defined in the natures for potential and flow.

3.6.1 Natures

A nature is a collection of attributes. Natures are declared at the top level (same level as discipline and module declarations). Nature declarations do not nest inside other nature, discipline, or module declarations.

nature_declaration ::=
    nature nature_identifier [ : parent_nature ] [ ; ]
        { nature_item }
    endnature

parent_nature ::=
    nature_identifier
  | discipline_identifier . potential_or_flow

nature_item ::= nature_attribute

nature_attribute ::= nature_attribute_identifier = nature_attribute_expression ;

potential_or_flow ::= potential | flow

nature_attribute_identifier ::=
    abstol | access | ddt_nature | idt_nature | units | identifier

A nature shall be defined between the keywords nature and endnature. Each nature shall have a unique identifier and shall include all required attributes.

nature current;
    units = "A";
    access = I;
    idt_nature = charge;
    abstol = 1u;
endnature

nature voltage;
    units = "V";
    access = V;
    abstol = 1u;
endnature

3.6.1.1 Derived Natures

A nature can be derived from an already declared nature by following the new nature name with a colon (:) and the name of the parent nature. The derived nature inherits all attributes of the parent and can declare additional attributes or override attribute values (with restrictions for predefined attributes).

A nature not derived from any other nature is called a base nature.

nature ttl_curr;
    units = "A";
    access = I;
    abstol = 1u;
endnature

// An alias
nature ttl_net_curr : ttl_curr;
endnature

nature new_curr : ttl_curr;    // derived, but different
    abstol = 1m;               // modified for this nature
    maxval = 12.3;             // new attribute for this nature
endnature

3.6.1.2 Attributes

There are five predefined attributes. User-defined attributes can also be defined in a nature.

AttributeRequiredDerivation RuleValue TypeDescription
abstol Required for base natures Derived natures may change it; if unspecified, inherited from parent Real Tolerance measure for convergence. Specifies the maximum negligible value for signals associated with the nature.
access Required for base natures Illegal for derived natures to change; always inherited from parent Identifier (not a string) Identifies the name for the access function. When the nature binds a potential, names the potential access function; when it binds a flow, names the flow access function.
idt_nature Optional (default: the nature itself) May be overridden in derived nature, but the new value shall be related (share the same base nature) to the parent's idt_nature Nature name (not a string) Relationship between a nature and the nature representing its time integral. Can be self-referencing.
ddt_nature Optional (default: the nature itself) May be overridden in derived nature, but the new value shall be related (share the same base nature) to the parent's ddt_nature Nature name (not a string) Relationship between a nature and the nature representing its time derivative. Can be self-referencing.
units Required for base natures Illegal for derived natures to define or change; always inherited from parent String Binding between the access function value and its units. Used by simulators to annotate signals and in net compatibility checking.

3.6.1.3 User-Defined Attributes

A nature can specify additional user-defined attributes. A user-defined attribute is declared in the same manner as any predefined attribute. The name shall be unique in the nature and the assigned value shall be constant.

3.6.2 Disciplines

A discipline description consists of specifying a domain type and binding any natures to potential or flow.

discipline_declaration ::=
    discipline discipline_identifier [ ; ]
        { discipline_item }
    enddiscipline

discipline_item ::=
    nature_binding
  | discipline_domain_binding
  | nature_attribute_override

nature_binding ::= potential_or_flow nature_identifier ;

potential_or_flow ::= potential | flow

discipline_domain_binding ::= domain discrete_or_continuous ;

discrete_or_continuous ::= discrete | continuous

nature_attribute_override ::= potential_or_flow . nature_attribute

A discipline shall be defined between the keywords discipline and enddiscipline. Each discipline shall have a unique identifier. Discipline declarations are at the top level (same level as nature and module declarations).

3.6.2.1 Nature Binding

Each discipline can bind a nature to its potential and flow.

The access function defined in the nature bound to potential describes signal-flow obeying Kirchhoff's Potential Law (KPL). The access function defined in the nature bound to flow describes a quantity obeying Kirchhoff's Flow Law (KFL).

Disciplines with two natures are conservative disciplines; their nets are conservative nets. Conservative disciplines shall not have the same nature for both potential and flow. Disciplines with a single nature are signal-flow disciplines; their nets are signal-flow nets.

Conservative discipline:

discipline electrical;
    potential Voltage;
    flow Current;
enddiscipline

Signal-flow disciplines:

discipline voltage;
    potential Voltage;
enddiscipline

discipline current;
    flow Current;
enddiscipline

Multi-disciplinary example (DC motor):

module motorckt;
    parameter real freq=100;
    electrical gnd; ground gnd;
    electrical drive;
    rotational shaft;
    motor m1 (drive, gnd, shaft);
    vsine #(.freq(freq), .ampl(1.0)) v1 (drive, gnd);
endmodule

module motor(vp, vn, shaft);
    inout vp, vn, shaft;
    electrical vp, vn;
    rotational shaft;
    parameter real Km = 4.5, Kf = 6.2;
    parameter real j = 0.004, D = 0.1;
    parameter real Rm = 5.0, Lm = 0.02;
    analog begin
        V(vp, vn) <+ Km*Theta(shaft) + Rm*I(vp, vn)
                      + ddt(Lm*I(vp, vn));
        Tau(shaft) <+ Kf*I(vp, vn) - D*Theta(shaft)
                      - ddt(j*Theta(shaft));
    end
endmodule

3.6.2.2 Domain Binding

The domain attribute takes two possible values: discrete or continuous. Signals with continuous-time domains are real valued.

discipline electrical;
    domain continuous;
    potential Voltage;
    flow Current;
enddiscipline

discipline ddiscrete;
    domain discrete;
enddiscipline

The domain attribute is optional. The default is continuous for disciplines which specify nature bindings. It is an error for a discipline to have domain discrete if it has nature bindings.

3.6.2.3 Natureless Disciplines and Domainless Disciplines

A discipline with no nature bindings is a natureless discipline. Such disciplines may have a domain binding or may be domainless (no domain binding and no nature binding), allowing the domain to be determined by connectivity.

The domain binding of a discipline with nature bindings defaults to continuous if not specified. A discipline with nature bindings cannot be a domainless discipline.

discipline natureless;
    domain continuous;
enddiscipline

discipline domainless
enddiscipline
Domainless disciplines are deprecated. The definition of a domainless discipline may be made an error in future versions.

3.6.2.4 Discipline of Nets and Undeclared Nets

A module may have nets without discipline declarations. If such a net appears bound only to ports in module instantiations, it may have no declaration at all or may be declared with a net type such as wire, tri, wand, wor, etc. If referenced in behavioral code, it must have a net type.

In these cases, the net shall be treated as having no discipline. If referenced in behavioral code, it shall be treated as having no discipline with a domain binding of discrete; otherwise it shall have no discipline and no domain binding.

3.6.2.5 Overriding Nature Attributes from Discipline

A discipline can override the value of the bound nature for predefined attributes (except as restricted by 3.6.1.2). The syntax uses the keyword flow or potential, the hierarchical separator ., the attribute name, and an assignment to the new value.

nature ttl_curr;
    units = "A";
    access = I;
    abstol = 1u;
endnature

nature ttl_volt;
    units = "V";
    access = V;
    abstol = 100u;
endnature

discipline ttl;
    potential ttl_volt;
    flow ttl_curr;
    flow.abstol = 10u;
enddiscipline

3.6.2.6 Deriving Natures from Disciplines

A nature can be derived from the nature bound to the potential or flow in a discipline. The nature declaration includes the discipline name followed by . and the keyword flow or potential. If the nature binding changes, the derived nature automatically inherits the attributes for the changed nature.

nature ttl_net_curr : ttl.flow;     // from the example in 3.6.2.5
endnature
// abstol = 10u as modified in ttl

nature ttl_net_volt : ttl.potential; // from the example in 3.6.2.5
    abstol = 1m;                     // modified for this nature
    maxval = 12.3;                   // new attribute for this nature
endnature

3.6.2.7 User-Defined Attributes

Like natures, a discipline can specify user-defined attributes.

3.6.3 Net Discipline Declaration

Each net_discipline declaration associates nets and regs with an already declared discipline.

net_declaration ::=
    ...
  | discipline_identifier [ range ] list_of_net_identifiers ;
  | discipline_identifier [ range ] list_of_net_decl_assignments ;
    ...

range ::= [ msb_constant_expression : lsb_constant_expression ]

list_of_net_decl_assignments ::= net_decl_assignment { , net_decl_assignment }

list_of_net_identifiers ::= ams_net_identifier { , ams_net_identifier }

net_decl_assignment ::= ams_net_identifier = expression

If a range is specified, the net is a vector net (bus); otherwise it is a scalar net.

electrical [MSB:LSB] n1;      // MSB and LSB are parameters
voltage [5:0] n2, n3;
magnetic inductor;
ddiscrete [10:1] connector1;

A net used for modeling a conservative system shall have a discipline with both access functions (potential and flow). When modeling a signal-flow system, the discipline can have only potential access functions. When modeling a discrete system, the discipline can only have domain discrete.

Nets declared with a natureless discipline or without a discipline do not have declared natures, so they cannot be used in analog behavioral descriptions (access functions are not known). However, they can be used in structural descriptions, inheriting natures from the ports of connected module instances.

3.6.3.1 Net Descriptions

Nets can be declared with a desc attribute:

(* desc="drain terminal" *) electrical d;

If a net is also a module port, the description attribute may be specified on the port declaration line. If specified in both the net discipline declaration and the port declaration, the last attribute value shall be used (the tool can warn about duplicates).

3.6.3.2 Net Discipline Initial (Nodeset) Values

Nets with continuous disciplines may have initializers on their net discipline declarations; nets of non-continuous disciplines may not.

electrical a = 5.0;
electrical [0:4] bus = '{2.3,4.5,,6.0};
mechanical top.foo.w = 250.0;

The initializer shall be a constant_expression and is used as a nodeset value for the potential of the net by the analog solver. For analog buses, a constant array expression is used. A null value in the constant array indicates no nodeset value for that element.

If different nets of a node have conflicting initializers, initializers on hierarchical net declarations take precedence. If there are multiple hierarchical declarations, the declaration on the highest level wins. If there are multiple conflicting initializers at the same level, it is a race condition.

3.6.4 Ground Declaration

Each ground declaration is associated with an already declared net of continuous discipline. The node associated with the net will be the global reference node. The net must be assigned a continuous discipline.

net_declaration ::=
    ...
  | ground [ discipline_identifier ] [ range ] list_of_net_identifiers ;
module loadedsrc(in, out);
    input in;
    output out;
    electrical in, out;
    electrical gnd;
    ground gnd;
    parameter real srcval = 5.0;
    resistor #(.r(10K)) r1(out,gnd);
    analog begin
        V(out) <+ V(in,gnd)*2;
    end
endmodule

3.6.5 Implicit Nets

Nets can be used in structural descriptions without being declared. In this case, the net's discipline and domain binding will be determined by discipline resolution.

module top(i1, i2, o1, o2, o3);
    input i1, i2;
    output o1, o2, o3;
    electrical i1, i2, o1, o2, o3;
    // ab1, ab2, cb1, cb2 are implicit nets, not declared
    blk_a a1( i1, ab1 );
    blk_a a2( i2, ab2 );
    blk_b b1( ab1, cb1 );
    blk_b b2( ab2, cb2 );
    blk_c c1( o1, o2, o3, cb1, cb2);
endmodule

3.7 Real Net Declarations (wreal)

The wreal (real net) data type represents a real-valued physical connection between structural entities. A wreal net shall not store its value. If no driver is connected, its value shall be zero (0.0). Unlike other digital nets which have an initial value of 'z, wreal nets shall have an initial value of zero.

Wreal nets can only be connected to compatible interconnect and other wreal or real expressions. They cannot be connected to any other wires, although connection to explicitly declared 64-bit wires can be done via $realtobits and $bitstoreal. Compatible interconnect are nets of type wire, tri, and wreal. When two nets connected by a port are of type wreal and wire/tri, the resulting single net is assigned as wreal. Connection to other net types results in an error.

net_declaration ::=
    ...
  | wreal [ discipline_identifier ] [ range ] list_of_net_identifiers ;
  | wreal [ discipline_identifier ] [ range ] list_of_net_decl_assignments ;
module drv(in, out);
    input in;
    output out;
    wreal in;
    electrical out;
    analog begin
        V(out) <+ in;
    end
endmodule

module top();
    real stim;
    electrical load;
    wreal wrstim;
    assign wrstim = stim;
    drv f1(wrstim, load);
    always begin
        #1 stim = stim + 0.1;
    end
endmodule

3.8 Default Discipline

The `default_discipline compiler directive specifies a default discrete discipline to be applied to any discrete net without an explicit discipline declaration, as part of discipline resolution.

3.9 Disciplines of Primitives

For digital primitives the domain is discrete and the discipline is set via `default_discipline. For analog primitives, the discipline is defined by the port_discipline attribute on that instance. If no attribute is found, it acquires the discipline of other compatible continuous disciplines connected to that net segment. If no disciplines are connected, the default discipline is set to electrical.

3.10 Discipline Precedence

The discipline of a net can be specified in multiple ways:

  • The discipline name can appear in the declaration of the net.
  • The discipline name can be used in a declaration which makes an out-of-context reference to the net from another module.

Discipline conflicts are resolved using this order of precedence:

  1. A declaration from a module other than the one the net belongs to, using an out-of-module reference: 
    module example1;
    electrical example2.net;
endmodule
  2. The local declaration of the net: 
    module example2;
    electrical net;
endmodule
  3. Discipline resolution

It is not legal to have two different disciplines at the same level of precedence for the same net.

3.11 Net Compatibility

Certain operations require nets to be compatible. The following rules apply:

Discrete Domain Rule: Digital nets with the same signal value type (real, integer) are compatible if their disciplines are compatible (discipline has a discrete domain or is empty).

Signal Domain Rule: It shall be an error to connect two ports or nets of different domains unless there is a connect statement defined between the disciplines.

Signal Connection Rule: It shall be an error to connect two ports or nets of the same domain with incompatible disciplines.

3.11.1 Discipline and Nature Compatibility

Discipline compatibility rules:

RuleDescription
Self Rule (Discipline)A discipline is compatible with itself.
Natureless Discipline RuleA natureless discipline is compatible with all other disciplines of the same domain.
Domainless Discipline RuleA domainless discipline is compatible with all disciplines (no nature or domain conflict). Domainless disciplines are deprecated.
Domain Incompatibility RuleDisciplines with different domain attributes are incompatible.
Potential Incompatibility RuleDisciplines with incompatible potential natures are incompatible.
Flow Incompatibility RuleDisciplines with incompatible flow natures are incompatible.

Nature compatibility rules:

RuleDescription
Self Rule (Nature)A nature is compatible with itself.
Non-Existent Binding RuleA nature is compatible with a non-existent discipline binding.
Base Nature RuleA derived nature is compatible with its base nature.
Derived Nature RuleTwo natures are compatible if derived from the same base nature.
Units Value RuleTwo natures are compatible if they have the same value for the units attribute.

Compatibility examples given these declarations:

nature Voltage;
    access = V; units = "V"; abstol = 1u;
endnature

nature Current;
    access = I; units = "A"; abstol = 1p;
endnature

nature highvoltage: Voltage;
    abstol = 1;
endnature

nature Position;
    access = X; units = "m"; abstol = 1u;
endnature

nature Force;
    access = F; units = "N"; abstol = 1n;
endnature

discipline electrical;
    potential Voltage; flow Current;
enddiscipline

discipline highvolt;
    potential highvoltage; flow Current;
enddiscipline

discipline sig_flow_v;
    potential Voltage;
enddiscipline

discipline sig_flow_x;
    potential Position;
enddiscipline

discipline rotational;
    potential Position; flow Force;
enddiscipline

discipline natureless;
    domain continuous;
enddiscipline

discipline domainless;
enddiscipline

discipline ddiscrete;
    domain discrete;
enddiscipline

discipline continuous_elec;
    domain continuous; potential Voltage; flow Current;
enddiscipline
  • Voltage and highvoltage are compatible natures (derived from the same base nature).
  • electrical and highvolt are compatible disciplines (natures for both potential and flow are derived from the same base natures).
  • electrical and sig_flow_v are compatible (same potential nature; flow does not exist in sig_flow_v).
  • electrical and rotational are incompatible (potential and flow natures are not derived from the same base natures).
  • electrical and sig_flow_x are incompatible (potential natures are not derived from the same base nature).
  • natureless is compatible with all other disciplines of the same domain (continuous).
  • domainless is compatible with all other disciplines.
  • electrical and ddiscrete are incompatible (different domains). A connect statement is required.
  • electrical and continuous_elec are compatible (default domain for electrical is continuous; same potential and flow natures).

3.12 Branches

A branch is a path between two nets. If both nets are conservative, the branch is a conservative branch and defines a branch potential and a branch flow. If one net is a signal-flow net, the branch is a signal-flow branch and defines either a branch potential or a branch flow, but not both.

Each branch declaration is associated with two nets (the branch terminals) from which it derives a discipline. Only one net need be specified; the second defaults to ground. The disciplines for the specified nets shall be compatible.

Branches can be explicitly (named branches) or implicitly declared. Unnamed branches are created by applying an access function to a net or pair of nets. If applied to a single net, the branch is formed between that net and the global reference node (ground). There shall be at most one unnamed branch between any two nets (in addition to any number of named branches).

branch_declaration ::=
    branch ( branch_terminal [ , branch_terminal ] ) list_of_branch_identifiers ;
  | port_branch_declaration

port_branch_declaration ::=
    branch ( < port_identifier > ) list_of_branch_identifiers ;
  | branch ( < hierarchical_port_identifier > ) list_of_branch_identifiers ;

branch_terminal ::=
    net_identifier
  | net_identifier [ constant_expression ]
  | net_identifier [ constant_range_expression ]
  | hierarchical_net_identifier
  | hierarchical_net_identifier [ constant_expression ]
  | hierarchical_net_identifier [ constant_range_expression ]

list_of_branch_identifiers ::=
    branch_identifier [ range ] { , branch_identifier [ range ] }

If one terminal is a vector net, the other shall be a scalar net or a vector net of the same size. When both terminals are vectors, the scalar branches connect to corresponding scalar nets of the vector terminals. When one terminal is a vector and the other is a scalar, each element of the vector branch connects to the scalar terminal.

If the range of the vector branch is not specified, indexing starts at 0:

electrical [3:5]a;
electrical [1:3]b;
branch (a,b) br1; // Branch br1 is of size 3 and can be indexed from 0 to 2

3.12.1 Port Branches

A port branch is a branch between the upper and lower connections of a port, used to access the flow into a port of a module. A port branch is scalar if the port identifier is scalar, vector if the port identifier is a vector port.

module current_sink(p);
    electrical p;
    branch (<p>) probe_p;
    analog
        $strobe("current probed is %g", I(probe_p));
endmodule

3.13 Namespace

3.13.1 Nature and Discipline

Natures and disciplines are defined at the same level of scope as modules. Identifiers defined as natures or disciplines have global scope.

3.13.2 Access Functions

Each access function name, defined before a module is parsed, is automatically added to that module's namespace unless there is another identifier defined with the same name. The access function of each base nature shall be unique.

3.13.3 Net

The scope rules for net identifiers follow the same rules as for any other identifier, except nets can only be declared in the port of a module or in the module itself. A net cannot be declared local to a block. Access functions are uniquely defined for each net based on its discipline. The hierarchical reference character (.) can be used to reference a net across the module boundary.

3.13.4 Branch

The scope rules for branch identifiers are the same as for net identifiers. A branch can only be declared inside a module scope; it cannot be declared local to a block. Access functions are uniquely defined for each branch based on its discipline. The hierarchical reference character (.) can be used to reference a branch across the module boundary.
