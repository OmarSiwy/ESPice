Chapter 7: Mixed-Signal

7.1 Overview

Mixed-signal design involves analog and digital domains coexisting within the same system. Verilog-AMS provides mechanisms for cross-domain interaction, allowing analog modules described with continuous-time behavioral equations to interoperate with digital modules described with event-driven logic.

The key challenges in mixed-signal simulation are:

  • Bridging the fundamentally different representations: continuous waveforms (analog) vs. discrete logic states (digital).
  • Synchronizing two different simulation engines: an analog solver (e.g., Newton-Raphson with adaptive timestep) and a digital event scheduler.
  • Resolving the discipline of interconnect nets when analog and digital ports meet.

Verilog-AMS addresses these challenges through connect modules, discipline resolution, and connect rules, which together automate the insertion of interface elements at domain boundaries.

The mechanisms described in this chapter apply to full Verilog-AMS designs. Pure Verilog-A (analog-only) modules do not require connect modules or discipline resolution, but understanding these concepts is essential when Verilog-A modules are instantiated within a mixed-signal hierarchy.

7.2 Connect Modules

A connect module is a special-purpose module that bridges analog and digital domains. Connect modules are declared using the connectmodule keyword and are automatically inserted by the simulator at points where nets of incompatible disciplines meet (see 7.5).

A connect module has exactly two ports: one in each domain. It contains behavioral code that converts signals between the two disciplines.

Syntax 7-1 -- Connect Module Declaration

connectmodule_declaration ::=
    { attribute_instance } connectmodule connectmodule_identifier
        ( port_declaration , port_declaration ) ;
        { module_item }
    endmodule

A connect module shall have exactly two ports. One port shall be of a continuous (analog) discipline and the other shall be of a discrete (digital) discipline. The direction of signal conversion is determined by the port directions (input, output, or inout).

Example: Analog-to-Digital Connect Module

connectmodule a2d (input electrical ain, output logic dout);
    parameter real vh = 2.7;    // voltage threshold for logic high
    parameter real vl = 0.5;    // voltage threshold for logic low
    parameter real tr = 10n;    // rise time for cross detection

    reg dout_val;

    initial dout_val = 1'bx;

    always begin
        @(cross(V(ain) - vh, +1))
            dout_val = 1'b1;
        @(cross(V(ain) - vl, -1))
            dout_val = 1'b0;
    end

    assign dout = dout_val;
endmodule

Example: Digital-to-Analog Connect Module

connectmodule d2a (input logic din, output electrical aout);
    parameter real v0 = 0.0;    // voltage for logic 0
    parameter real v1 = 3.3;    // voltage for logic 1
    parameter real vx = 1.65;   // voltage for logic x
    parameter real tr = 1n;     // transition rise time
    parameter real tf = 1n;     // transition fall time
    parameter real r0 = 100.0;  // output resistance

    real vout;

    always @(din) begin
        case (din)
            1'b0:    vout = v0;
            1'b1:    vout = v1;
            default: vout = vx;
        endcase
    end

    analog
        V(aout) <+ transition(vout, 0, tr, tf) + I(aout) * r0;
endmodule
Connect modules may contain both analog blocks and digital always/initial blocks, as they inherently straddle both domains. The simulator treats them as mixed-signal modules regardless of their content.

7.3 Discipline Resolution

When multiple ports of different disciplines connect to the same net, the simulator must determine the net's discipline. This process is called discipline resolution and occurs during elaboration, after all generate constructs have been evaluated and paramsets selected (see 6.9).

7.3.1 Compatibility

Two disciplines are compatible if they share the same domain (continuous or discrete) and their natures are compatible (see 3.11). Two natures are compatible if they have the same units and access function name, or if one is derived from the other.

ConnectionCompatible?Action
electrical – electricalYesDirect connection, no conversion needed
electrical – voltageYesCompatible natures, resolved by algorithm
electrical – logicNoConnect module required
logic – logicYesDirect connection
electrical – rotationalNoIncompatible analog disciplines, error

7.3.2 Resolution Algorithm

The discipline resolution algorithm processes each net in the design:

  1. Collect all disciplines of all ports connected to the net.
  2. If all disciplines are compatible, select the most specific discipline (the one that declares both potential and flow natures, or the one with the tightest abstol).
  3. If disciplines are from different domains (continuous vs. discrete), mark the net as a mixed-signal boundary. The net is split, and a connect module is inserted at the boundary.
  4. If disciplines are from the same domain but incompatible (e.g., electrical and rotational), it shall be an error.

7.3.3 Precedence Rules

When multiple compatible disciplines are candidates, the following precedence applies:

  • An explicitly declared discipline on the net takes highest precedence.
  • A discipline with both potential and flow natures takes precedence over one with only a potential nature.
  • Among equally qualified disciplines, the discipline with the smallest abstol is selected.
  • If resolution is still ambiguous, the simulator shall issue a warning and select the discipline of the first port encountered in source order.

7.4 Connect Rules

Connect rules specify which connect modules the simulator shall insert at domain boundaries. They are declared using a connectrules block, which contains one or more connect statements.

Syntax 7-2 -- Connect Rules

connectrules_declaration ::=
    connectrules connectrules_identifier ;
        { connect_statement }
    endconnectrules

connect_statement ::=
    connect connectmodule_identifier
        [ #( list_of_parameter_assignments ) ]
        discipline_identifier , discipline_identifier ;
  | connect connectmodule_identifier
        [ #( list_of_parameter_assignments ) ]
        discipline_identifier , discipline_identifier
        { , discipline_identifier , discipline_identifier } ;
  | connect discipline_identifier , discipline_identifier
        merged ;

Each connect statement associates a connect module with a pair of disciplines. When the simulator encounters a net at the boundary of those two disciplines, it instantiates the specified connect module.

connectrules default_rules;
    connect a2d                         electrical, logic;
    connect d2a                         logic, electrical;
    connect bidir #(.vh(2.7), .vl(0.5)) electrical, logic;
endconnectrules

Parameter Overrides

Connect rules may override the default parameter values of the connect module using the standard parameter override syntax. This allows a single connect module definition to be reused with different threshold voltages, transition times, or output impedances for different discipline pairs.

connectrules cmos33_rules;
    connect a2d #(.vh(2.0), .vl(0.8))   electrical, logic;
    connect d2a #(.v1(3.3), .v0(0.0))   logic, electrical;
endconnectrules

connectrules cmos18_rules;
    connect a2d #(.vh(1.2), .vl(0.4))   electrical, logic;
    connect d2a #(.v1(1.8), .v0(0.0))   logic, electrical;
endconnectrules

Merged Connect

The merged keyword in a connect statement indicates that the two disciplines are compatible and shall be treated as a single merged net without inserting a connect module. This is used to override the default resolution when the user knows the disciplines are interchangeable in context.

connectrules merged_example;
    connect electrical, voltage merged;
endconnectrules

7.5 Automatic Insertion

The simulator automatically inserts connect modules during elaboration when it detects a domain boundary on a net. The process occurs after discipline resolution (see 7.3) and after connect rules have been parsed.

7.5.1 Insertion Process

  1. For each net in the design, collect all connected port disciplines.
  2. Perform discipline resolution. If the net has ports from both continuous and discrete domains, it is a mixed-signal boundary.
  3. At each boundary, determine the direction of conversion from the port directions:
    • An analog output driving a digital input requires an A/D connect module.
    • A digital output driving an analog input requires a D/A connect module.
    • inout ports require a bidirectional connect module.
  4. Search the active connect rules for a matching connect module.
  5. Instantiate the connect module with a unique instance name generated by the simulator.

7.5.2 Port Compatibility and Direction

Analog PortDigital PortRequired Connect Module
outputinputA/D (analog-to-digital)
inputoutputD/A (digital-to-analog)
inoutinputA/D
inputinoutD/A
inoutinoutBidirectional
If no matching connect rule is found for a given discipline pair, the simulator shall issue an error. The design must provide connect rules for all domain crossings that occur in the elaborated hierarchy.

7.5.3 Example: Full Mixed-Signal Hierarchy

// Top-level mixed-signal testbench
module top;
    electrical ana_sig;
    wire dig_sig;
    logic dig_out;

    // Analog VCO drives a digital counter
    vco #(.freq(1e6)) osc (.out(ana_sig));
    counter #(.bits(8)) cnt (.clk(ana_sig), .q(dig_out));
    //                             ^--- domain boundary: electrical -> logic
    //                             simulator inserts a2d here

    // Digital PWM drives an analog filter
    pwm_gen pwm (.in(dig_out), .out(dig_sig));
    lpf #(.fc(10e3)) filt (.in(dig_sig), .out(filtered));
    //                           ^--- domain boundary: logic -> electrical
    //                           simulator inserts d2a here
endmodule

7.6 Signal Access Across Domains

Verilog-AMS provides several mechanisms for accessing signals across domain boundaries without explicit connect modules.

7.6.1 Accessing Analog Signals from Digital Blocks

Digital blocks cannot directly probe analog node voltages or branch currents. To access analog values from a digital context, use one of the following approaches:

  • wreal nets: A continuous-valued wire in the digital domain (see 6.5.3). A wreal net carries a real-valued signal without quantization, but is scheduled by the digital event engine.
  • Connect modules: The A/D connect module samples the analog signal and drives a digital output.
  • $realtime: Returns the current simulation time as a real value, usable in both domains.
// Using wreal to pass analog values into digital logic
module sampler (input electrical ain, input wire clk, output wreal dout);
    real sampled;

    always @(posedge clk) begin
        sampled = V(ain);   // V() probe within an analog-aware context
    end

    assign dout = sampled;
endmodule
The V() and I() access functions are only valid inside analog blocks or connect modules. Accessing them from purely digital always or initial blocks requires a mixed-signal simulator that supports cross-domain probing, which is implementation-defined.

7.6.2 Accessing Digital Signals from Analog Blocks

Analog blocks can detect digital events and read digital state through connect modules. The D/A connect module converts logic levels to continuous voltages or currents that the analog solver can process.

// Analog block responding to a converted digital signal
module dac_filter (input electrical d_converted, output electrical filtered);
    parameter real fc = 1e3;
    parameter real r = 1.0 / (6.2832 * fc * 1e-12);

    analog begin
        // d_converted arrives from a d2a connect module as a voltage
        I(filtered) <+ (V(d_converted) - V(filtered)) / r;
        I(filtered) <+ 1e-12 * ddt(V(filtered));
    end
endmodule

7.6.3 Driver Resolution for wreal

Unlike multi-valued digital nets, a wreal net shall have at most one driver. If multiple drivers are connected to a wreal net, the simulator shall issue an error. This restriction exists because real-valued signals have no natural resolution function analogous to digital wire-AND or wire-OR.

7.7 Mixed-Signal Restrictions

The following restrictions apply to mixed-signal designs:

7.7.1 Contribution Restrictions

  • Contribution statements (<+) are only permitted inside analog blocks. They cannot appear in digital always, initial, or assign statements.
  • A contribution shall only target branches whose nets are of a continuous discipline. Contributing to a net of discrete discipline is an error.
  • Indirect contributions (via hierarchical branch references) across a domain boundary are not permitted.

7.7.2 Event Interaction Restrictions

  • Analog event functions (@(cross(...)), @(above(...)), @(timer(...))) are only valid within analog blocks.
  • Digital event controls (@(posedge ...), @(negedge ...)) are only valid within digital procedural blocks.
  • An analog block shall not use @(posedge ...) or @(negedge ...). Use @(cross(...)) with the appropriate edge argument instead.
  • A digital block shall not use @(cross(...)), @(above(...)), or @(timer(...)).

7.7.3 Structural Restrictions

  • A net connecting ports of incompatible disciplines from different domains requires a connect rule. If no applicable connect rule exists, it is an elaboration error.
  • A net connecting ports of incompatible disciplines within the same domain (e.g., electrical and rotational) is always an error; no connect module can bridge same-domain incompatible disciplines.
  • Connect modules shall not be instantiated explicitly by the user. They are inserted only by the simulator during elaboration.
  • A connect module shall have exactly two ports. Declaring a connect module with fewer or more ports is an error.

7.7.4 Timing and Synchronization

The analog and digital simulation engines operate with different notions of time advancement. The analog engine uses adaptive timestepping controlled by local truncation error estimates; the digital engine advances to the next scheduled event. The mixed-signal simulator must synchronize these two engines at domain boundaries.

  • Analog-to-digital transitions generate digital events. The cross() function in an A/D connect module forces the analog solver to locate the threshold crossing precisely.
  • Digital-to-analog transitions are smoothed by the transition() filter in the D/A connect module to provide a continuous waveform to the analog solver.
  • The simulator shall ensure that analog breakpoints coincide with digital events at domain boundaries, so that connect module outputs are always current.
The details of analog-digital synchronization are implementation-defined. The LRM specifies the semantic contract (connect modules see consistent signal values) but not the synchronization algorithm.
