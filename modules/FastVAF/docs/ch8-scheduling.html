Chapter 8 — Scheduling Semantics

This chapter describes how the simulation kernel manages time advancement, convergence, and the interaction between analog and digital solvers. Understanding the scheduling semantics is essential for writing models that converge reliably and simulate efficiently.

8.1 Overview

A Verilog-AMS simulator contains two cooperating engines: the analog solver, which handles continuous-time behavior, and the digital event scheduler, which handles discrete-event behavior. In a pure Verilog-A context only the analog solver is active.

The analog solver is responsible for:

  • Selecting timepoints at which the circuit is evaluated
  • Formulating and solving the system of nonlinear equations at each timepoint
  • Iterating until convergence criteria are satisfied
  • Advancing simulation time after a converged solution is accepted
  • Scheduling breakpoints requested by analog event functions

The simulation flow at each timepoint follows a evaluate-check-accept cycle:

for each timepoint:
    repeat
        evaluate all analog blocks          // builds the equation system
        solve the linearized system         // Newton-Raphson update
        check convergence                   // compare against tolerances
    until converged or iteration limit exceeded
    if converged:
        accept the solution
        advance time (select next timepoint)
    else:
        reject the timepoint
        reduce timestep and retry

8.2 Analog Simulation Kernel

The analog kernel uses Newton-Raphson iteration to solve the system of nonlinear algebraic-differential equations generated from the circuit topology and the behavioral descriptions in all analog blocks.

8.2.1 Newton-Raphson Iteration

At each timepoint the simulator constructs a system of equations of the form F(x) = 0, where x is the vector of unknown node voltages and branch currents. The Newton-Raphson method linearizes this system around the current estimate xk:

J(x_k) * delta_x = -F(x_k)
x_{k+1} = x_k + delta_x

where J is the Jacobian matrix of partial derivatives. The simulator evaluates all analog blocks to compute F(xk) and the entries of J. This process repeats until convergence or until the iteration limit is reached.

8.2.2 Iteration Loop

Each Newton-Raphson iteration proceeds as follows:

  1. Evaluate: All analog blocks are executed with current node voltage and branch current estimates. Contribution statements populate the right-hand side vector and Jacobian matrix entries.
  2. Solve: The linearized matrix equation is solved to produce a correction vector delta_x.
  3. Update: The solution vector is updated: xk+1 = xk + delta_x.
  4. Check: Convergence tests are applied (see 8.3). If all tests pass, the solution is accepted. Otherwise, iteration continues from step 1.
Note: Because all analog blocks are re-evaluated at every iteration, expressions must not have side effects that accumulate across iterations. Contribution statements use the <+ operator which resets the accumulated value at the start of each iteration.

8.2.3 Iteration Limit

Simulators impose a maximum iteration count (typically 25-150 iterations). If convergence is not achieved within this limit, the simulator may:

  • Reduce the timestep and retry (in transient analysis)
  • Report a non-convergence error (in DC analysis)
  • Apply source stepping or Gmin stepping to aid convergence

8.3 Convergence

The simulator determines that a solution has converged when the correction at every node and branch is negligibly small relative to the solution values and the applicable tolerances.

8.3.1 Convergence Criteria

Two tests are applied at each node voltage v and branch current i:

TestCriterionDescription
Node voltage|delta_v| < reltol * |v| + vntolChange in node voltage is small
Branch current|delta_i| < reltol * |i| + abstolChange in branch current is small
KCL residual|F_node| < reltol * max_current + abstolKCL error at each node is small

Here reltol is the relative tolerance (typically 1e-3), vntol is the absolute voltage tolerance, and abstol is the absolute current tolerance derived from the nature definition.

8.3.2 Tolerances from Nature Definitions

The abstol attribute in a nature definition provides the absolute tolerance for convergence testing. For the standard electrical discipline:

nature Current;
    units      = "A";
    access     = I;
    abstol     = 1e-12;   // 1 pA
endnature

nature Voltage;
    units      = "V";
    access     = V;
    abstol     = 1e-6;    // 1 uV
endnature

The tolerance for a branch is derived from the nature of the flow through that branch. For the ddt() and idt() operators, an explicit tolerance argument can override the nature-derived value.

8.3.3 Convergence Aids

Verilog-A provides several constructs to help the simulator converge on difficult circuits.

8.3.3.1 The $limit Function

The $limit() function restricts how much a signal can change between Newton-Raphson iterations, preventing the solver from overshooting into non-physical regions.

$limit ( access_function_reference , limiter_function
    [ , arg_list ] )

The most common usage is with the built-in "pnjlim" limiter for PN junction voltages:

module diode(a, c);
    inout a, c;
    electrical a, c;
    parameter real is = 1e-14;
    real vd_lim;
    analog begin
        // Limit the junction voltage to prevent Newton overshoot
        vd_lim = $limit(V(a,c), "pnjlim", $vt, is*V(a,c));
        I(a,c) <+ is * (limexp(vd_lim / $vt) - 1);
    end
endmodule
Note: Without $limit(), the exponential I-V characteristic of a diode can cause Newton-Raphson to oscillate or diverge. The limiter restricts the voltage step to a safe range each iteration while still converging to the true solution.

8.3.3.2 The limexp Function

The limexp() function is a convergence-friendly replacement for exp(). It behaves identically to exp() at the converged solution but internally limits the argument change between iterations.

// Without limexp -- may fail to converge
I(a,c) <+ is * (exp(V(a,c) / $vt) - 1);

// With limexp -- much better convergence
I(a,c) <+ is * (limexp(V(a,c) / $vt) - 1);

limexp() is an analog operator; it maintains internal state across iterations. It shall not be used inside conditional statements unless the condition is a constant expression.

8.3.3.3 The $bound_step Function

The $bound_step() function limits the size of the next timestep. It does not force a specific timestep but provides an upper bound.

$bound_step ( max_step )

The max_step argument shall be a positive-valued expression. The simulator shall ensure the next timestep does not exceed max_step. Multiple calls to $bound_step() within a single evaluation cycle are cumulative -- the smallest bound wins.

// Ensure at least 100 points per cycle of a VCO
module vco(out, in);
    inout out, in;
    electrical out, in;
    parameter real fc = 1e6, kv = 1e6;
    real freq, phase;
    analog begin
        freq = fc + kv * V(in);
        $bound_step(1.0 / (100.0 * freq));
        phase = idt(2.0 * `M_PI * freq);
        V(out) <+ sin(phase);
    end
endmodule
Note: $bound_step() is critical for models that generate signals whose frequency is not visible to the simulator's automatic timestep control. Without it, the solver may take steps that are too large and miss oscillation cycles entirely.

8.4 Timestep Control

The analog solver selects timesteps to balance accuracy against simulation speed. The timestep selection algorithm considers multiple constraints simultaneously.

8.4.1 Local Truncation Error

The primary mechanism for timestep control is local truncation error (LTE) estimation. The simulator estimates the error introduced by the numerical integration method (ddt(), idt()) and adjusts the timestep to keep this error within tolerance.

The LTE depends on the integration order and the higher-order derivatives of the solution. For a method of order p, the LTE is proportional to hp+1, where h is the timestep. The simulator estimates LTE and selects h such that:

LTE < reltol * |solution| + abstol

8.4.2 Breakpoints

Breakpoints are specific times at which the simulator must place a timepoint. They are generated by:

SourceDescription
cross()Schedules a breakpoint near a detected threshold crossing
above()Schedules a breakpoint near a detected threshold crossing from below
timer()Schedules breakpoints at specified absolute times
$bound_step()Constrains maximum step size (not a breakpoint per se, but limits advancement)
$discontinuity()Informs the simulator of a known discontinuity, triggering a breakpoint
SimulatorStart time, stop time, print intervals, and output times

At a breakpoint, the simulator places a timepoint at or very near the requested time. The integration order may be reduced at breakpoints to maintain accuracy across potential discontinuities.

8.4.3 Timestep Bounds

The effective timestep is bounded by:

h_min <= h <= min(h_lte, h_bound_step, h_breakpoint, h_max)

where:
    h_min          = simulator minimum timestep
    h_lte          = timestep from LTE control
    h_bound_step   = smallest $bound_step() value from current evaluation
    h_breakpoint   = distance to the next scheduled breakpoint
    h_max          = simulator maximum timestep (user-configurable)

8.4.4 Timestep Rejection

If Newton-Raphson fails to converge at a timepoint, the simulator rejects the timepoint, reduces the timestep, and retries. Repeated rejections with progressively smaller timesteps indicate a modeling problem (infinite slope, missing $discontinuity() call, or incorrect limiting).

8.5 DC Analysis

DC analysis computes the operating point of the circuit -- the steady-state solution with all time derivatives set to zero. This is the starting point for transient, AC, and noise analyses.

8.5.1 Operating Point Computation

During DC analysis, the simulator solves F(x) = 0 with all ddt() operators returning zero and all idt() operators returning their initial condition (or zero if none is specified). The analysis() function can be used to detect DC context:

analog begin
    if (analysis("dc"))
        $strobe("DC operating point: V(b,e) = %g", V(b,e));
end

8.5.2 Analysis Identifiers for DC

Several analysis() identifiers relate to the DC operating point:

IdentifierReturns 1 when
"dc"A standalone DC analysis or a DC sweep is active
"static"Any DC solution is being computed, including the initial operating point before transient or AC
"ic"The simulator is applying initial conditions (the .ic phase of the DC solve)
"nodeset"The simulator is applying nodeset values as initial guesses
Note: analysis("static") is true during all DC solves, including the operating point that precedes a transient or AC analysis. analysis("dc") is true only during a standalone DC or DC sweep analysis. This distinction matters for models that need different behavior during transient initialization versus a true DC sweep.

8.5.3 Nodeset and Initial Conditions

The simulator supports two mechanisms to aid DC convergence:

  • Nodeset values provide initial guesses for node voltages. They are applied during the first iteration(s) and then released, allowing the solver to find the true solution. Detected via analysis("nodeset").
  • Initial conditions force node voltages to specified values during the DC solve. They override the solver for those nodes. Detected via analysis("ic").
// Apply different behavior during nodeset phase
analog begin
    if (analysis("nodeset"))
        V(internal) <+ 0.7;  // guide solver toward forward-bias
    else
        I(a,c) <+ is * (limexp(V(a,c)/$vt) - 1);
end

8.5.4 DC Sweep

In a DC sweep, the simulator performs a sequence of operating point analyses while varying one or more parameters or source values. At each sweep point:

  1. The swept parameter is updated
  2. The previous solution is used as the initial guess
  3. Newton-Raphson iteration is performed until convergence
  4. The converged solution is recorded

The initial_step("dc") event fires at the first sweep point. The final_step("dc") event fires at the last sweep point.

8.6 Transient Analysis

Transient analysis computes the time-domain response of the circuit. The simulator advances through time, solving the full nonlinear algebraic-differential system at each timepoint.

8.6.1 Integration Methods

The simulator discretizes continuous-time derivatives and integrals using numerical integration methods. The two most common methods are:

MethodOrderFormulaProperties
Backward Euler (BE)1ddt(x) ~ (x_n - x_{n-1}) / hUnconditionally stable, first-order accurate, high numerical damping
Trapezoidal (TRAP)2ddt(x) ~ 2*(x_n - x_{n-1})/h - ddt_prevSecond-order accurate, no numerical damping, may produce ringing

Most simulators use trapezoidal integration by default and fall back to backward Euler at breakpoints or when ringing is detected. Higher-order methods (Gear's BDF methods) are also available in some simulators for stiff systems.

8.6.2 The ddt() Operator in Transient

The ddt() operator computes the time derivative of its argument using the current integration method. In transient analysis it produces a non-zero result; in DC analysis it returns zero.

// Capacitor: I = C * dV/dt
I(p,n) <+ c * ddt(V(p,n));

8.6.3 The idt() Operator in Transient

The idt() operator computes the time integral of its argument. The optional second argument provides the initial condition for DC analysis.

// Inductor: V = L * dI/dt  (equivalent: I = (1/L) * integral(V))
I(p,n) <+ idt(V(p,n), 0) / L;

8.6.4 Charge-Based Formulation

For better numerical accuracy, capacitances should be formulated in terms of charge rather than capacitance times ddt() of voltage. The charge-based formulation avoids errors when capacitance is voltage-dependent:

// Voltage-dependent capacitor -- CORRECT charge-based formulation
real q_junc;
analog begin
    q_junc = -2 * cjo * sqrt(phi * (phi - V(a,c)));
    I(a,c) <+ ddt(q_junc);
end

// INCORRECT: loses dC/dV term when C depends on voltage
// I(a,c) <+ C(V(a,c)) * ddt(V(a,c));  // WRONG
Note: The charge-based formulation I <+ ddt(Q(V)) automatically produces the correct dQ/dV * dV/dt via the chain rule when the simulator differentiates. The direct C*ddt(V) formulation misses the dC/dV * dV/dt term, which can cause charge non-conservation and inaccurate results in circuits with nonlinear capacitances.

8.6.5 Initial Conditions from DC

Transient analysis begins from the operating point computed by DC analysis. All node voltages, branch currents, and internal states of analog operators (idt(), transition(), laplace_*, etc.) are initialized from the DC solution. The initial_step("tran") event fires at the first transient timepoint after DC initialization.

8.7 AC and Small-Signal Analysis

AC analysis linearizes the circuit around the DC operating point and computes the small-signal frequency response. The analog block is not re-evaluated during AC analysis; instead, the Jacobian from the operating point is used.

8.7.1 Linearization

During AC analysis, each nonlinear element is replaced by its small-signal equivalent. Contribution statements of the form:

I(a,c) <+ f(V(a,c));

are linearized to produce a small-signal conductance g = df/dV evaluated at the operating point.

8.7.2 Frequency-Domain Interpretation of Operators

In AC analysis, time-domain operators acquire frequency-domain meaning:

OperatorTransientAC (small-signal)
ddt(x)Time derivative dx/dtMultiplied by jω
idt(x)Time integralDivided by jω
laplace_zp()Laplace-domain filter (time convolution)Transfer function H(jω) evaluated directly
laplace_nd()Laplace-domain filterN(jω)/D(jω)
zi_zp(), zi_nd()Z-domain filterH(ejωT)

8.7.3 AC Stimulus

The ac_stim() function provides the small-signal excitation source for AC analysis. It returns zero in all other analyses.

ac_stim ( [ analysis_name [ , mag [ , phase ] ] ] )
// AC voltage source with 1V magnitude, 0 phase
module ac_source(p, n);
    inout p, n;
    electrical p, n;
    parameter real dc_val = 0;
    analog begin
        V(p,n) <+ dc_val + ac_stim("ac", 1.0, 0);
    end
endmodule

In DC analysis, ac_stim() returns zero, so the source contributes only dc_val. In AC analysis, it provides the stimulus at the specified magnitude and phase.

8.8 Noise Analysis

Noise analysis is a small-signal analysis that computes the spectral density of noise at specified output nodes. Like AC analysis, it operates on the linearized circuit at the DC operating point.

8.8.1 Noise Source Functions

Noise contributions are specified using dedicated noise functions within contribution statements:

FunctionSpectral DensityTypical Use
white_noise(pwr)Constant: S(f) = pwrThermal noise, shot noise
white_noise(pwr, name)Constant, named for reportingNamed noise contributors
flicker_noise(pwr, exp)S(f) = pwr / fexp1/f noise (typically exp=1)
flicker_noise(pwr, exp, name)Named flicker noiseNamed 1/f contributors
noise_table(vector)Piecewise-linear from tableMeasured or tabulated noise data
noise_table(vector, name)Named table noiseNamed tabulated contributors
// Resistor with thermal noise
module resistor(p, n);
    inout p, n;
    electrical p, n;
    parameter real r = 1k from (0:inf);
    analog begin
        V(p,n) <+ r * I(p,n);
        I(p,n) <+ white_noise(4 * `P_K * $temperature / r, "thermal");
    end
endmodule

// MOSFET with channel noise and 1/f noise
I(d,s) <+ white_noise(4 * `P_K * $temperature * gm * 2/3, "channel");
I(d,s) <+ flicker_noise(kf * ids / (cox * leff * leff), af, "flicker");

8.8.2 Noise Computation

During noise analysis, the simulator:

  1. Computes the DC operating point
  2. Linearizes the circuit (same as AC)
  3. At each frequency point, evaluates the noise spectral density of each noise source
  4. Propagates each noise contribution through the linearized network to the output
  5. Sums all contributions (noise powers add, not amplitudes) to produce the total output noise spectral density

8.8.3 Input-Referred Noise and Noise Figure

The simulator can report noise referred to the input by dividing the output noise spectral density by the squared magnitude of the transfer function from input to output. Noise figure is computed as:

NF = 10 * log10(total_input_noise / source_noise)

The optional name argument in noise functions allows the simulator to report the contribution of individual noise sources to the total, enabling noise budgeting and optimization.

8.9 Mixed-Signal Scheduling

In a Verilog-AMS environment, the analog solver and the digital event scheduler must be synchronized. The analog solver runs in continuous time while the digital scheduler runs in discrete event time.

8.9.1 Synchronization Points

The two solvers synchronize at specific points:

  • Analog-to-digital events: When an analog event function (cross(), above(), timer()) generates an event that triggers digital behavior
  • Digital-to-analog updates: When a digital signal change affects an analog expression (e.g., via transition() or slew() filters)
  • Connect module evaluations: When connect modules convert between analog and digital domains

8.9.2 Analog Event Detection Resolution

Analog events detected by cross() and above() are resolved to within the specified time and expression tolerances. The simulator iterates on the timestep to place a timepoint near the crossing. The event is then injected into the digital event queue at the resolved time.

// Clock recovery: analog cross triggers digital sampling
module clk_recovery(data_in, clk_out);
    input data_in;
    output clk_out;
    electrical data_in;
    reg clk_out;
    parameter real threshold = 0.0;

    analog begin
        @(cross(V(data_in) - threshold, +1, 1e-12, 1e-6))
            ;  // timestep control only
    end

    always @(above(V(data_in) - threshold))
        clk_out = ~clk_out;
endmodule

8.9.3 Causal vs. Non-Causal Interaction

Analog-to-digital and digital-to-analog interactions must be causal: the effect cannot precede the cause. The transition() and slew() filters introduce a delay to ensure causality when a digital signal drives an analog expression. Similarly, analog event functions detect crossings and schedule digital events at or after the crossing time.

Verilog-AMS note: Pure Verilog-A modules do not use mixed-signal scheduling. The content of this section applies only when analog and digital domains coexist in a Verilog-AMS simulation.

8.10 Tolerances and Accuracy

Tolerances appear in multiple contexts throughout the simulation. This section summarizes their relationships.

8.10.1 Summary of Tolerance Sources

ToleranceSourceTypical ValueAffects

abstol (current)Nature definition1e-12 AKCL convergence, branch current convergence
abstol (voltage)Nature definition1e-6 VNode voltage convergence

8.10.2 Explicit Tolerance in Operators

The ddt() and idt() operators accept an optional tolerance argument that overrides the nature-derived tolerance. This is important when the operator acts on a quantity whose natural tolerance differs from the branch tolerance:

// Explicit tolerance on ddt -- use the abstol of the charge nature
I(a,c) <+ ddt(q_junc, abstol_charge);

// Using nature attribute reference for tolerance
I(a,c) <+ ddt(q_junc, a.potential.abstol);

8.10.3 Relationship Between Tolerances

The convergence criterion at each node combines relative and absolute tolerances:

converged if: |delta| < reltol * |value| + abstol

The relative tolerance reltol dominates when signal magnitudes are large. The absolute tolerance abstol dominates when signal magnitudes are near zero, preventing the simulator from iterating to achieve meaningless precision on negligible signals.

Choosing tolerances involves tradeoffs:

  • Too tight: Excessive iterations, slow simulation, possible non-convergence
  • Too loose: Inaccurate results, charge non-conservation, missed events
  • Mismatched: A current abstol inconsistent with the voltage abstol and typical impedance levels can cause the solver to over-refine one domain while under-refining another
Practical guideline: For most circuits, the default tolerances from the standard discipline definitions work well. Override only when modeling circuits with unusual signal ranges (e.g., sensor interfaces with picoamp currents may need a tighter current abstol).
